Part B · System design (HLD)

Cart and checkout for a large e-commerce site

The LLD runs the whole checkout in one process, with a fake payment gateway that answers instantly. In production, inventory, orders and payments are separate services, payment confirmation arrives asynchronously, and a flash sale sends thousands of buyers at a single SKU.

H1. Functional requirements

In scopeOut of scope
  • A cart that persists across devices: add, update quantity, remove, see live prices
  • Apply one coupon, with validity, minimum order value and usage limits
  • Checkout: price the cart, reserve stock, take payment (UPI, cards, wallets), create the order
  • Order history, order status, cancellation and refund
  • Flash sales: limited stock at a fixed start time
  • Catalog search and browsing (a separate system)
  • Shipping, warehouses and fulfilment: consumers of OrderConfirmed
  • Multi-seller split orders. Mention them: one order becomes several shipments.
  • Tax calculation beyond a flat GST rate

H3. Capacity estimation

Assumptions: 20M DAU. 30% of them edit a cart, about 5 edits each. Carts are read 5 times per DAU per day (cart page, mini-cart badge). 1M orders a day, 3 lines each. Peak is 5× average, and a flash sale is 20×.

What the numbers tell you

Overall checkout throughput is modest: 230/s fits a single Postgres primary. The hard part is contention, not volume: 1.7k writes a second against a single inventory row, all trying to take the last few units. That decides the inventory design.

The difference from the LLD: checkout returns PENDING_PAYMENT and a payment action, not a confirmed order. Real payments (UPI collect, 3-D Secure) finish on the user's phone or the bank's page, and confirmation arrives later by webhook.

H5. High-level design

{{cc-arch}}

One service per business area, each with its own database. Checkout orchestrates the saga. Every state change writes an outbox row in the same transaction, and a relay publishes it to Kafka.

  • Cart is a key-value document per user, read-heavy and cached. Prices are not stored in the cart: they are fetched live from pricing, which is cached for 60 seconds.
  • Checkout owns orders and the saga. It talks to inventory and payment synchronously for the steps the user waits on, and consumes payment events asynchronously.
  • Inventory is the only writer of stock. It keeps reservations with an expiry time, and a sweeper releases the expired ones.
  • Payment wraps the PSPs behind one interface (Strategy, as in the LLD), stores every webhook, and runs reconciliation.
{{cc-seq}}

The checkout saga. The user waits for steps 1–9 only. Confirmation is asynchronous, and every step can be retried safely because each one is keyed: the idempotency key, the reservation id, the order id sent to the PSP, and the PSP's event id.

orders + inventory (key tables)
  • CHECK (available >= 0) is the last line of defence. Even buggy code can't oversell.
  • orders.version gives optimistic concurrency for status changes: UPDATE … SET status = 'CONFIRMED', version = version + 1 WHERE id = $1 AND status = 'PENDING_PAYMENT'. A duplicate webhook then updates 0 rows and does nothing.
  • Coupon usage limits are a counter row (coupons.used) incremented with WHERE used < max_uses, in the same transaction that creates the order.

H7. Detailed component design

1 · Inventory reservation

reserve (one transaction, lines sorted by sku to avoid deadlocks)

The status guard makes commit and release mutually exclusive. If the sweeper releases a reservation at the same moment the payment webhook commits it, only one of them changes the row. Section 4 below covers the case where the sweeper wins.

2 · The hot SKU in a flash sale

TechniqueHowCost
Admission gateRedis DECR sale:{sku}:tokens, seeded with the stock. Only buyers who get a token ≥ 0 reach the database.The database row sees about as many writes as there are units in stock, not 100k buyers.
Split countersStock spread across N rows (sku#0 … sku#7). Reserve from a random bucket and try the next one when it's empty.N× write throughput. "Out of stock" now means checking all N buckets.
Waiting roomUsers are queued at the edge and let in at a fixed rateProtects every service downstream. It's the best user experience under extreme load.
Per-user limitA unique row per (sale, user)Stops scripts buying everything

Redis is only a gate. The Postgres row stays the source of truth, so a lost Redis key can let a few extra buyers through to the database, where the conditional update still refuses them.

3 · Payment integration

  • The payment intent is created with idempotency_key = order_id at the PSP, so a retried "create" never makes a second charge.
  • Webhooks: verify the HMAC signature, then INSERT INTO payment_events (psp_event_id UNIQUE …). A duplicate violates the constraint and we return 200 without doing anything. Then publish PaymentSucceeded through the outbox.
  • The reconciler runs every minute. For each order PENDING_PAYMENT older than 15 minutes it asks the PSP for the status. Webhooks get lost, and the reconciler is what makes the system correct anyway.
  • Daily settlement reconciliation compares the PSP's settlement file with our captured payments and flags mismatches for finance.

4 · Late payment after the reservation expired

The user pays at 15:30 for a reservation that expired at 15:29, and the stock went to someone else. On PaymentSucceeded, checkout tries to commit. If the reservation is already RELEASED, it tries to re-reserve. If that succeeds the order is confirmed. If not, the order becomes CANCELLED with reason STOCK_EXPIRED, an automatic refund is issued, and the user is told. Prevention is better: make the reservation TTL longer than the PSP's payment window, and tell the PSP to expire the payment link before the reservation expires.

H8. Interviewer questions and counters

Q1Why a saga? Use a distributed transaction (2PC) across orders, inventory and payment.

Answer

The PSP is an external system that doesn't take part in our transactions, and payment can take minutes (UPI approval on the phone). 2PC would hold locks on stock rows for that long and block on the coordinator. A saga uses local transactions plus compensations: release stock, refund. Each step is idempotent and the orchestrator's state is in the orders table, so a crash simply resumes.

Push-back: "Sagas leave the system temporarily inconsistent."

Yes, and the states say so honestly: PENDING_PAYMENT with stock held. The user sees "payment pending", which is the truth. The invariants that matter (stock never negative, never charged twice) hold at every step, because they're enforced inside single-database transactions.

Q2Orchestration or choreography for the saga?

Answer

Orchestration, by checkout. The order flow is the core business process: one place should own its state machine, its timeouts and its compensations, and you can debug an order by reading one row. Choreography, where each service reacts to the others' events, is fine for side effects such as email, analytics and search indexing, and those consume OrderConfirmed.

Push-back: "The orchestrator is a single point of failure."

It's stateless pods over a replicated database. If a pod dies, another one picks the saga up from the order row and the outbox. It's a hotspot of logic, not of availability.

Q3Why reserve stock at checkout and not when the item is added to the cart?

Answer

Most carts are abandoned. Reserving at add-to-cart lets idle carts lock up stock, and a competitor could hoard it with bots. Reserving at checkout holds stock only for people who are actually paying, and only for 15 minutes. The cart shows "only 2 left" as information, not a promise. (The LLD's C3 covers this from the code side.)

Push-back: "The user loses the item at checkout. Bad experience."

For scarce items, do a short soft hold when the user enters checkout (the address step), and use a waiting room for drops. For ordinary stock the chance is tiny and the message is clear.

Q4Why not keep stock in Redis? It's faster.

Answer

Redis failover can lose acknowledged writes, because replication is asynchronous. With stock that means overselling or phantom stock. Keep Redis as an admission gate in front, and let the database row (with its CHECK constraint) have the final say.

Push-back: "Postgres can't do 1.7k/s on one row."

Correct. That's why the gate exists: once the tokens run out, the database stops seeing traffic. If the stock itself is large (say 50k units), split the counter across buckets.

Q5The webhook arrives before the client's checkout call has even returned. Problem?

Answer

It can happen with fast payment methods. The order row is committed (step 5) before the intent is created (step 6), so the webhook always finds the order. The confirm is a conditional update from PENDING_PAYMENT, so the order doesn't care which arrives first.

Q6How do you guarantee the event is published if the service crashes right after committing?

Answer

Transactional outbox. The event row is written in the same transaction as the state change. A relay (polling, or Debezium reading the database's change log) publishes it and marks it sent. Delivery is at least once, so consumers deduplicate on event id. Writing to the database and then calling Kafka separately ("dual write") loses events on crashes.

Q7Microservices from day one?

Answer

Not necessarily. A modular monolith with the same boundaries (cart, checkout, inventory, payment, each owning its own tables, talking through interfaces and an in-process outbox) gets 90% of the design benefit, and real transactions are a bonus. Split a module out when it needs independent scaling or its own team: inventory during sales, and payment for PCI compliance.

Q8The price changes between viewing the cart and paying. Which price is charged?

Answer

The price on the order snapshot, which is taken at checkout. Checkout sends the cart version it priced. If pricing has changed since, return 412 with the new totals, and the client shows "price updated, confirm?". After the order is created, its lines are frozen: the webhook confirms the stored total and never re-prices.
