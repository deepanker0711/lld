Part B · System design (HLD)

A centralised logging platform

The LLD is the library inside each service. The HLD question is what happens next: collecting logs from 20,000 pods, making them searchable within seconds, keeping them affordably for months, and never letting logging take an application down.

H1. Functional requirements

In scopeOut of scope

  • Search by time range, service, level, any structured field, trace id, and free text

  • Multi-tenant: per-team quotas, retention and access control
  • PII redaction before storage; retention tiers and archive
  • Metrics and traces (related pipelines, mentioned in Q3)
  • Full SIEM and security analytics
  • Dashboards beyond simple counts over time

What the numbers tell you

Storage design decides the cost by a factor of 20: indexing every word of 43 TB a day needs hundreds of terabytes of SSD, while indexing only labels and scanning compressed chunks in object storage needs about 30 TB of cheap storage. Queries are rare but heavy, so the design shifts cost from ingest time (indexing) to query time (scanning), and requires every query to say which services and what time range it wants.

H5. High-level design

{{lf-arch}}

Logs move through buffers at every hop: the library's ring buffer, the agent's disk buffer, Kafka. Each hop can absorb a slow next hop for a while without pushing back on the app.

  • Library (the LLD): writes structured JSON to stdout through a bounded asynchronous appender. It adds request id, trace id and service, and redacts known keys.
  • Agent per node: tails container output, adds Kubernetes labels (namespace, pod, service), batches, compresses, and buffers to local disk when ingest pushes back.
  • Ingest gateway: authenticates the tenant, enforces quotas, rejects malformed batches, and produces to Kafka with acks=all. It returns 200 only after Kafka has the data, so the agent can safely advance its checkpoint.
  • Kafka decouples ingest from storage and lets several consumers read the same stream: processors, the alert engine and live tail.
  • Processors parse, redact, sample (keep 100% of WARN and above, 10% of DEBUG) and write to the hot store in bulk. Old data rolls over to object storage, then to an archive tier.
  • Query service splits a query by time and shard, runs the pieces in parallel against hot and cold storage, merges by timestamp, and enforces limits.
{{lf-seq}}

The processor commits its Kafka offset only after the store has the data. A crash means replaying a batch (a duplicate), not losing it.

Choice: label index plus compressed chunks in object storage as the default tier, which keeps cost under control. Add a small full-text or columnar tier for the last 24 h of ERROR and WARN, where most investigations start.

data layout
  • Never make request id or user id a label. Each value would create its own stream and the index would explode. Keep them as fields in the line, and use per-chunk bloom filters to skip chunks.
  • Partition by tenant and time, so retention is "delete prefixes older than N days", never row-by-row deletes.

H7. Detailed component design

1 · Client library: never block the app

This is the LLD: check the level before doing anything (lazy messages), put the record in a bounded queue, and let a background flusher write it out. When the queue is full, drop DEBUG and INFO first and keep WARN and above (the BufferedAppender policy), and increment a logs_dropped_total{level} metric so the loss is visible. A synchronous write to a slow disk or the network on the request thread is the classic way logging causes an outage (L2).

2 · Agent and backpressure

  • The agent checkpoints its read position per file and advances it only after ingest returns 200. That gives at-least-once delivery across restarts.
  • If ingest returns 429 or 503, or is unreachable, the agent spills to a disk buffer (for example 5 GB per node, roughly an hour) and retries with jittered backoff. That way the agents don't all reconnect at the same moment when ingest recovers.
  • When the disk buffer is full, drop by priority and report the drops as metrics. Never fill the node's disk: that would kill the pods logging to it.

3 · Ingest, quotas and Kafka

  • Per-tenant token buckets in MB/s, with a burst allowance. A noisy team gets 429s, and its agents buffer, without affecting anyone else.
  • Kafka topics are partitioned by hash(tenant, service), so lines from one stream stay ordered, with enough partitions (say 512) to scale consumers. Ordering across streams is by timestamp, decided at query time.
  • Processors are a consumer group. Lag is the key health metric and drives autoscaling.

4 · Redaction

  • Layer 1, in the library: known keys (password, cardNumber, authorization) are masked before the line exists. This is redactKeys from the LLD.
  • Layer 2, in the pipeline: regex and pattern detectors for card numbers (with a Luhn check), Aadhaar or PAN formats, emails and tokens. Matches are masked, and the event is counted per service so the owning team gets a ticket to fix it at the source.
  • Raw data never reaches storage. If you need the unredacted line for debugging, the answer is to log better fields, not to keep secrets.

5 · Query execution

  • Parse the query. Use the label selector and time range to find chunk ids from the index, then drop chunks with the bloom filter if there's a trace id or request id.
  • Split the work by time into 15-minute pieces, run them in parallel across querier pods, stream results back merged by timestamp, and stop at the limit.
  • Guardrails: a maximum time span per query (24 h unless you go through an async export), a maximum bytes scanned per tenant per minute, and a cache for repeated dashboard queries.

H8. Interviewer questions and counters

Q1Why put Kafka between the agents and storage? Agents could write directly.

Answer

Three reasons. It absorbs bursts and outages in storage, which is the most fragile part (indexing, compaction), without pushing back on 20k agents. Several consumers can read the same stream: storage, the alert engine, live tail, a SIEM. And storage can be replayed after a bug. Without it, every storage hiccup becomes agent buffering on every node.

Push-back: "Kafka is another big system to run."

True. Below a few hundred MB/s, agents writing straight to the store with disk buffers is a reasonable start. Add Kafka when you need fan-out or the store can't absorb bursts.

Q2Elasticsearch or a Loki-style store?

Answer

It depends on how people query and on budget. Full-text indexing of everything costs about 20× more at this volume (H3), and most queries are "this service, this time window, this string", which label filtering plus a scan handles well. So I'd use the label-indexed store by default, plus a small full-text tier for recent errors.

Push-back: "Our engineers search across all services for a customer id."

Then that field needs an index. Use per-chunk bloom filters on it, or send a copy of the logs with that field to a columnar store keyed by it. Pay to index the one field you search on, not every word.

Q3Why not just use metrics and traces? Logs are expensive.

Answer

They answer different questions. Metrics tell you that something is wrong (cheap, aggregated). Traces tell you where (sampled request paths). Logs tell you why (detailed events). Reduce log volume by moving counts into metrics, sampling DEBUG, and raising levels at runtime only when needed (the LLD's PUT /loggers/{name}/level, L3). Putting trace ids in log lines connects all three.

Q4The whole logging pipeline is down. What happens to the apps?

Answer

Nothing visible. The library writes to stdout asynchronously, and the agent buffers to disk for about an hour. Beyond that the agent drops low-priority lines and counts them. No application thread ever waits for the pipeline. The cost is a gap or delay in logs, which is an observability incident, not a customer incident.

Push-back: "Audit logs must not be lost."

Audit events don't belong in the best-effort log pipeline. Write them to the database transactionally (an outbox) or to a durable topic with acknowledged writes. Different guarantee, different path.

Q5One team suddenly logs 10× more and slows everyone down.

Answer

Per-tenant quotas at ingest (429 for that tenant only), separate Kafka partitions so their lag doesn't block other teams' consumers, and per-tenant query limits. Alert the team on their own drop and throttle metrics. If they need more, it's a budget conversation, and you can show cost per team because volume is tracked per tenant.

Q6Are logs in order?

Answer

Within one stream (one pod's output), yes: one Kafka partition, one chunk sequence. Across pods, only roughly, by timestamp, and clocks drift by milliseconds. For causality across services, use the trace id and span parent links, not timestamps. The query merges by timestamp and breaks ties by stream and sequence, so results are at least deterministic.

Q7How do you make sure no card numbers end up in storage?

Answer

Defence in depth: typed log fields with masking in the library, pipeline detectors that mask and report, a periodic scan of samples from storage, and a code review rule against logging whole request bodies. Report each detection to the owning team, because masking in the pipeline hides the bug without fixing it.

Q8Alert when checkout logs more than 50 errors a minute. Run it as a query every minute?

Answer

No. Evaluate it on the stream: the alert engine consumes Kafka, keeps a sliding-window counter per rule and group key, and fires on the threshold with deduplication and a cool-down. Polling queries would scan storage every minute for every rule, and they'd be late by the ingest delay. For rate-style alerts, it's even better to emit a metric from the library and alert in the metrics system.
