Topic · Written · src/modules/auth

User Login

Register with a hashed password, then log in to get a short-lived access token (a signed JWT) and a long-lived refresh token (an opaque random string, stored only as a hash). The refresh token rotates every time it's used, and using an old one again revokes the whole session. Logout works instantly because every request checks that the session is still active. Failed logins lock the account, and the lock is per email so parallel guesses can't get around it.

Core ruleAccess = JWT 15 min · Refresh = rotating, hash stored
ConcurrencyKeyedMutex per email (hashing is async)
PatternsStrategy (hasher), Guard, Decorator
Demo filerequests/auth.http

1. Problem and scope

AskAssumption we build with
Identity?Email (trimmed, lower-cased, unique) + password. Social login and OTP are follow-ups.
Password rules?8–72 characters, at least one letter and one digit. The rules apply only at registration, so a password set under older rules can still log in.
Storage?scrypt with a random salt per user. The cost factor is stored inside the hash string, so you can raise it later without breaking existing passwords.
Tokens?Access JWT (HS256, 15 min) carries sub, sid and roles. Refresh token: 32 random bytes; the server keeps only its SHA-256.
Session length?7 days, measured from login. Refreshing does not extend it.
Logout?Takes effect immediately, including for access tokens that haven't expired yet. "Log out everywhere" and "log out that device" are supported.
Brute force?5 failures in a row lock the account for 15 min (429 with retryAfterMs). This holds even when the guesses arrive in parallel.
Enumeration?Same 401 message for an unknown email and a wrong password. The server also runs a hash check for unknown emails, so both cases take the same time.
Roles?USER, plus ADMIN. In the demo, registering with admin@example.com grants ADMIN. Admin routes are protected with @Roles(Role.ADMIN).

The session repository keeps two indexes. userId → sessions powers the "my devices" list and logout-all. refresh-token hash → session contains every hash the session has ever had, not just the current one. That is deliberate: when a rotated hash shows up again, the lookup finds its session, and that is how reuse is detected.

Token flow

login → use → refresh → reuse
POST /auth/login           → access A1 (15 min, sid=S)  + refresh R1     session S: hash(R1)
GET  /auth/me  Bearer A1   → verify signature + exp → session S active? → 200
POST /auth/refresh R1      → hash(R1) is current → rotate                 session S: hash(R2)
                           ← access A2 + refresh R2
POST /auth/refresh R1      → hash(R1) belongs to S but isn't current: REUSE
                           → revoke S (reason REFRESH_TOKEN_REUSE) → 401
GET  /auth/me  Bearer A2   → session S revoked → 401                  ← the thief's copy dies too

Tests (12)

  • Registration stores a salted hash and never returns it. Two registrations of the same email racing each other: exactly one succeeds.
  • A wrong password and an unknown email get the same 401.
  • 6 bad logins in parallel still trigger the lockout. After the 15 minutes pass (on the fake clock), login works again.
  • The access token expires at 15 minutes. A token with tampered claims, a token with alg=none, and a token signed with a different secret are all rejected.
  • Refresh rotation: reusing an old refresh token revokes the session, so the newest refresh token and access token are dead too.
  • Logging out kills that device's token but other devices keep working. Logout-all revokes every session. Revoking another user's session returns 404.

7. Senior follow-ups

U1Why not make the access token fully stateless and skip the session lookup?

Answer

You can, and many systems do. The trade-off is that a logged-out or stolen token keeps working until it expires. With a 15-minute lifetime that is often acceptable. When it isn't, keep the check but make it cheap. Revoking writes the session id to Redis with a TTL equal to the access token lifetime, and the guard does one EXISTS. The set only ever holds sessions revoked in the last 15 minutes, so it stays small.

Implementation change

revocation list
U2Ten services need to verify tokens. Do they all share the secret?

Answer

No. Switch to asymmetric signing (RS256 or EdDSA). Only the identity service holds the private key. Every other service verifies with the public key, which it fetches from a JWKS endpoint and caches. Each token carries a kid (key id) header, so you can rotate keys with no downtime: publish the new key, start signing with it, and retire the old key after the longest token lifetime has passed. A leaked verifier can't mint tokens.

Implementation change

jwks
U3A user has two tabs open. Both refresh at the same moment, and one gets logged out as "reuse".

Answer

That's the downside of strict rotation. You have two fixes. On the client, a single-flight refresh: one tab refreshes and the others wait for its result (via a BroadcastChannel, or a lock in a shared worker). On the server, a short grace window: when a token that was rotated less than about 10 seconds ago comes back, return the pair that was already issued instead of treating it as theft. Replays after the window are still treated as reuse. Keep the window short and tie it to the same session.

Implementation change

grace window
U4Where should the browser keep the tokens?

Answer

Keep the refresh token in an HttpOnly, Secure, SameSite=Strict cookie scoped to /auth/refresh. JavaScript can't read it, so an XSS attack can't steal it, and it's sent only to the refresh endpoint. Keep the access token in memory: a page reload calls refresh and gets a new one. Don't use localStorage, because any script injected into the page can read it. If the access token is also sent as a cookie, add CSRF protection, such as a double-submit token or SameSite plus checking Origin.

U5An attacker tries one password against 10,000 accounts (credential stuffing).

Answer

The per-account lockout never triggers, because each account sees only one failure. Add limits along other dimensions: per IP and per subnet with a sliding window (the rate limiter from the Keka handbook), plus a global failure-rate alarm. Check new passwords against known breach lists (k-anonymity range queries against HaveIBeenPwned). When a login looks risky (new device, new country, IP on a block list), show a CAPTCHA or require an OTP instead of blocking outright. Also, lockout can be abused: an attacker can lock someone else out on purpose. So prefer increasing delays, or exempt known devices.

U6Add "forgot password".

Answer

  • Request a reset: always return 202, whether or not the email exists. If it does, email a single-use token that is valid for 15 minutes. Store only its hash, just like a refresh token.
  • Confirm the reset: check the token's hash and expiry, set the new password, delete the token, and revoke every session. The point of a reset is to lock out anyone else who had access.
  • Abuse limits: rate-limit reset requests per email and per IP, so the endpoint can't be used to spam someone's inbox.

Implementation change

reset
U7Add OTP-based two-factor login.

Answer

Split login into two steps. Step 1: email and password are correct, so return a short-lived mfaToken (a signed token for "this user, step 1 done, valid 5 minutes"), not a session. Step 2: the client sends the mfaToken plus a TOTP code. The server checks the code against the user's TOTP secret, allowing ±1 time step for clock drift, and only then creates the session. Rate-limit step 2: a 6-digit code has only a million values. Offer one-time recovery codes, stored as hashes.

Implementation change

mfa
U8An admin removes a user's ADMIN role. Their existing access token still says ADMIN.

Answer

The token's roles are a snapshot taken when it was issued. There are three options, from least to most strict:

  • Accept up to 15 minutes of staleness. The next refresh picks up the new roles.
  • Bump a version number. Changing a user's roles increments their authzVersion. The token carries it, and the guard compares it with a cached value.
  • Revoke the user's sessions whenever their roles change.

For admin rights, use the version number or revocation. For everyday roles, staleness is usually fine.

8. Pitfalls

  • Hashing with SHA-256 or MD5. These are fast hashes, which is exactly what you don't want for passwords. Use a slow, salted one: scrypt, argon2 or bcrypt.
  • Comparing hashes or signatures with ===. Use timingSafeEqual.
  • Trusting the token header's alg. Pin it, or alg: none goes straight through.
  • Storing refresh tokens in plain text. Anyone who can read the database could then log in as anyone.
  • Different errors for "no such user" and "wrong password", or a fast path that skips hashing for unknown emails. Both leak which accounts exist.
  • Counting failures without a lock. Parallel guesses get past the lockout.
  • Refresh tokens that don't rotate, or rotation without reuse detection. A stolen token then lives forever.
  • Treating logout as client-side only (just delete the token). The token keeps working until it expires.
  • Returning passwordHash in any response, including admin lists.
  • Password rules on login. Users whose passwords predate the rules are locked out.
  • Returning 403 for a missing token. Unauthenticated is 401; authenticated but not allowed is 403.

60-second summary to say

Say this

"Users register with an email and a scrypt-hashed password with a random salt; the cost factor is stored inside the hash so it can be raised later. Login checks the password and creates a session: one per device. It returns a 15-minute HS256 access token carrying the user id, the session id and the roles, plus an opaque refresh token whose SHA-256 is all the server stores. Refreshing rotates that token. If an old one is ever presented again, someone has a copy, so the whole session is revoked. The guard verifies the signature and expiry, then checks the session is still active, so logout is immediate; at scale that check is a Redis revocation list. Login is serialised per email, so parallel guesses can't get past the five-failure lockout. Unknown emails and wrong passwords get the same answer in the same time. Roles are checked after authentication: 401 means who are you, 403 means you can't."

Cart & Checkout

The cart stores only product ids and quantities, and is priced fresh every time it's read. Checkout first validates every line, then reserves the stock and records the coupon use, all synchronously, before it waits on the payment. A successful payment confirms the order and clears the cart. A declined payment returns the stock and the coupon use, and leaves the cart as it was. Each user's checkout runs under its own lock and requires an Idempotency-Key. Together these stop a double-click, a client retry and two buyers racing for the last unit.

ConcurrencyLock per user + Idempotency-Key

7. Senior follow-ups

C1Ten app servers. How do you stop overselling?

Answer

Move the "check and reserve" into the database, as one conditional statement per line: UPDATE … SET available = available − q WHERE id = $1 AND available ≥ q. If it affects 0 rows, that line is out of stock. Run all lines in one transaction so the reservation is all-or-nothing. The CHECK (available ≥ 0) constraint is the safety net if the code ever gets it wrong. For flash sales with one very hot product, row contention becomes the bottleneck. Then pre-split the stock into N bucket rows and take from a random bucket, or keep the counter in Redis with an atomic DECRBY and reconcile later.

Implementation change

reserve in a transaction
C2The server crashes after charging but before confirming. Now what?

Answer

The order is stuck in PENDING_PAYMENT with stock reserved. Two things fix it:

  • A reconciler job: every minute, find PENDING_PAYMENT orders older than N minutes and ask the gateway for the payment's status by order id, which works because the order id was sent as the idempotency key. Captured → confirm. Not found or failed → release.
  • The gateway's webhook: it says "payment captured for order X". The same confirm runs, guarded by the state table so it happens only once.

Never release stock on a timer alone. A payment that was captured late would then have no stock to fulfil it.

Implementation change

reconciler (job scheduler)
C3Should items be reserved when added to the cart?

Answer

Usually no. Carts are abandoned most of the time, so reserving on add would lock stock that never sells. There are two exceptions. Flash sales and tickets reserve for a few minutes (see the movie booking hold). Very low-stock items can show "only 2 left" without reserving. If you do reserve on add, give the hold an expiry that is checked lazily on read, as the movie booking module does. That avoids a timer per cart.

C4The same Idempotency-Key arrives with a different cart.

Answer

That's a client bug, and silently returning the old order would hide it. Store a fingerprint (a hash of the request plus the cart snapshot) with the key. Same key and same fingerprint: replay. Same key and different fingerprint: 422. This module returns the existing order on any key reuse, because the cart is the request. The wallet module does the fingerprint check. Keys should also expire (after 24 hours, say) so the table doesn't grow forever.

C5Stack coupons, plus "buy 2 get 1 free" and category-specific offers.

Answer

Discounts stop being "one number off the subtotal". They become rules that read the lines and return line-level adjustments. Run them in a defined order (item-level offers, then cart-level coupons), with stacking rules ("only one cart coupon"; "BOGO doesn't stack with % off"). Record each adjustment on the order so the receipt explains itself, and so refunds of single items can be pro-rated.

Implementation change

promotion rules
C6Make checkout a saga: inventory, payment and orders are separate services.

Answer

The order service orchestrates the saga, in order:

  1. Create the order as PENDING.
  2. Ask inventory to reserve the stock.
  3. Ask payment to charge.
  4. On success, confirm, and inventory commits the reservation.

Each step has a compensation: release the reservation, refund the charge. Messages go through a transactional outbox, so "order PENDING" and the message "reserve stock" are committed together. Every consumer is idempotent, keyed by order id. Reservations expire on their own, so a stuck saga can't hold stock forever. Our single-process code already has the same shape: reserve, charge, then confirm or release.

8. Pitfalls

M2Why lazy expiry instead of a timer per hold?

Answer

A timer per hold means thousands of timers, and all of them are lost on a restart. With lazy expiry, correctness only needs holdExpiresAt to be stored. Any read that finds a lapsed hold expires it. The downside is that expired holds linger in storage until something reads them. A periodic sweep (the job scheduler) can clean them up for reporting, but correctness never depends on it. In Redis, the key's TTL does the same job.

M3Don't let users leave a single empty seat between two booked ones.

Answer

This is a seat-selection rule, so it belongs in a validator strategy that runs before the hold. For each affected row, simulate the row with the requested seats taken. A prepaid wallet with a double-entry ledger. Every movement of money writes a DEBIT and a CREDIT of the same amount, and the ledger is append-only. A wallet's balance is a cached sum of its entries, and a reconcile endpoint proves the two agree. Every one requires an Idempotency-Key, stored together with a fingerprint of the request. W1Two servers process transfers from the same wallet at the same moment.

Answer

Use one database transaction per transfer. It locks both wallet rows in a fixed order (by id, so two opposite transfers can't deadlock), checks the balance, updates both balances and inserts both entries. CHECK (balance ≥ 0) is the backstop. The other option is optimistic locking: UPDATE … SET balance = balance − x, version = version + 1 WHERE id = $1 AND version = $v AND balance ≥ x, retrying when it affects 0 rows. That scales better when conflicts are rare. The unique (initiator, idempotency_key) index stops a duplicate even if two servers receive the same retry.

W2Why keep a cached balance at all? Sum the ledger.

Answer

Summing millions of entries on every balance check and every transfer is too slow, and "check balance, then debit" needs a single row to lock. The ledger is the source of truth and the balance is a cache, kept correct because only post() writes it, in the same transaction as the entries. Reconciliation (nightly, plus spot checks) recomputes from the ledger and alerts on any difference. For very old accounts, store a snapshot (balance as of entry N) so a reconcile only sums the entries after N.

Answer

A timeout means you don't know, so it isn't a failure. Reversing would give the user money that may already have reached their bank. Keep the transaction PENDING with the wallet already debited, and settle it later. Options: poll the bank's status API using the transaction id (sent to the bank as the idempotency key), wait for the bank's webhook, or read the bank's end-of-day settlement file. Reverse only on a definite rejection. This module reverses on any error, which is fine for a fake rail. In production, split RailsDeclinedError (definite) from RailsTimeoutError (unknown).

8. Pitfalls

  • Floats for money, or mixing rupees and paise. Use integer paise everywhere.
  • wallet.balance += x in several places. Have exactly one function that writes entries and balance together.
  • Editing or deleting ledger entries to "fix" mistakes. Post reversing entries instead.
  • Single-entry ledgers (one row per transfer). You can't prove where the money went, or that none was created.
  • Creating the transaction record after calling the payment gateway. A retry charges twice.
  • Same Idempotency-Key with a different body silently accepted.
  • Checking the balance, then awaiting something, then debiting. Two withdrawals overdraw the account.
  • Reversing a payout on a timeout. The user is paid twice.

7. Senior follow-ups

S1A group has 50,000 expenses. Recomputing balances on every read is slow.

Answer

Keep a running balance table (group, member) → net, updated in the same transaction as each expense insert, delete and settlement. Each change only adds or subtracts that event's deltas, so it's O(participants), not O(history). The derived calculation stays as the reconciliation check. Pairwise needs a (group, a, b) table, still updated by deltas. Simplify is O(n log n) over members, not expenses, so it can still run on every read.

Implementation change

incremental
S2Is greedy optimal? Can you do fewer payments?

Answer

Greedy guarantees at most n − 1 payments, but not the minimum. The minimum is n minus the largest number of disjoint zero-sum subgroups. Example: balances {+3, +2, +2, −3, −4}. The optimum is 3 payments ({+3, −3} and {+2, +2, −4}), but greedy matches +3 with −4 first and ends up making 4. Finding the true minimum is NP-hard, because it contains subset-sum. For small groups (≤ 12 people) you can find it exactly with a bitmask dynamic programme over subsets: the cost is 2ⁿ, still tiny at that size. Splitwise-style apps use greedy or a heuristic, because 2 payments vs 3 rarely matters to users.

S3A trip abroad: some expenses in EUR, some in INR.

Answer

Store every expense in its original currency together with the exchange rate on the expense date. Keep balances per currency (a net map for each), so the history stays true to what was actually spent. When settling up, either settle each currency separately, or convert everything to one settlement currency at today's rate and show which rate was used. Don't convert at entry time and throw the original away. Rates move, and the record should show what really happened.

S4Someone edits an expense from ₹900 to ₹1200. What happens to past settlements?

Answer

Balances are derived, so editing the expense (recomputing its shares) is enough: everything downstream updates. Settlements stay as they were, because they're real payments that happened. Someone who had settled may now owe again, and the balances show it. Keep an audit trail (expense versions: who changed what, when), and notify the other participants. Editing in place is fine here, unlike a payment ledger, because these records describe what people owe each other, not money that moved.

S5Two people add expenses to the same group at the same moment.

Answer

Nothing conflicts: expenses are appended, and balances are a sum. This is a deliberate strength of the design. With the running-balance table (S1), concurrent updates use net = net + delta (an atomic increment), never read-modify-write, so there's no lost update. The only check that needs care is settle, which reads the balance to cap the amount. Two settlements racing could each pass. Lock the group's balance rows (SELECT … FOR UPDATE) for a settlement, or accept the overpay and let the balance go positive the other way, since it's a recorded real-world payment.

S6Recurring expenses: rent split every month.

Answer

Store a template (payer, amount, split, cron rule). A scheduled job creates the real expense each period. That's the job scheduler's recurring job, with an idempotency key of (templateId, period) so a retried run doesn't add rent twice. Editing the template changes future months only.

8. Pitfalls

  • Dividing in floats (1000 / 3 = 333.333…) and rounding each share. The shares stop adding up to the total.
  • Rounding every share up or down the same way. You end up a paisa short or over. Use largest remainder.
  • Storing balances and editing them by hand. They drift, and deleting an expense becomes a puzzle.
  • Always including the payer in the split. "I paid for your ticket" then becomes a 50/50 split.
  • Allowing a settlement larger than the debt, which silently turns into a debt the other way.
  • Letting members leave with an open balance. The money disappears.
  • Calling greedy "optimal" in the interview. Say "at most n − 1, the true minimum is NP-hard."
  • Comparing percentages as floats (33.33 + 33.33 + 33.34 ≠ 100 in floating point). Convert to basis points first.

F2Nearest-first isn't the best assignment. What would you do instead?

Answer

Greedy nearest-first is locally optimal but globally poor. Better options:

  • Stacking. Let one agent carry two orders from the same restaurant going the same way.

7. Senior follow-ups

L1Logs from 200 pods: how do you collect and search them?

Answer

Don't ship logs from inside the app. Write JSON lines to stdout, which this framework's console appender already does. A node agent (Fluent Bit, Vector) tails the container output, adds pod, node and service labels, and ships to the store: Loki (cheap, label-indexed) or Elasticsearch (full-text). The app stays simple, and a slow log backend can never block requests. Correlate across services by passing requestId (or a W3C traceparent) in headers, and put it in each service's LogContext.

L2Writing to a file synchronously is slowing requests down.

Answer

That's exactly what BufferedAppender is for: requests only push onto an array, and a timer or the batch size triggers the write. For files, use a write stream (fs.createWriteStream, with flags: 'a') and respect backpressure: if write() returns false, stop flushing until the 'drain' event fires. For very high volume, move formatting and writing to a worker thread (pino's transport model), so even JSON.stringify leaves the main thread. Always flush on shutdown; the module does so in onApplicationShutdown.

L3Turn on DEBUG for one user or one request in production, without flooding the logs.

Answer

Make the level check context-aware. A support engineer sets "debug for userId X for 10 minutes", and that rule goes in a small config store that is watched (Redis, or a config service). isEnabled first checks the normal effective level. If that says no, it checks whether the current LogContext matches an active debug rule. An x-debug: 1 header that only internal clients may send works the same way. Expire the rules automatically, so nobody leaves DEBUG on.

L4A hot loop logs 100,000 identical errors a second. How do you protect the system?

Answer

Add a rate-limiting processor in the chain. Key records by (logger, level, message template) and let N per second through. Then suppress the rest, and periodically emit one summary line: "suppressed 99,880 similar messages". That's a token bucket per key, like the rate limiter topic. Sample DEBUG and INFO by a percentage if needed, but never sample ERROR completely away: always keep the first few and the counts. The buffered appender's drop policy is the last line of defence.

L5Why not just use console.log or Nest's built-in Logger?

Answer

console.log has no levels, no structure, no context and no redaction, and it's synchronous to a TTY. Nest's Logger has levels and a context name, but no hierarchical runtime levels, no MDC, and no pluggable sinks. In real projects, use pino (or winston) and plug it in as Nest's logger (app.useLogger), so framework logs and app logs share one pipeline. The point of this module is that you can explain what those libraries do inside: hierarchy, processors, appenders, context and backpressure.

L6The context leaks between requests sometimes. Why?

Answer

AsyncLocalStorage follows the async chain from the point where run() started. Context is lost or leaks in three situations:

  • Work scheduled outside run(). A shared connection pool or a cached promise created by another request carries that request's context.
  • Callback libraries that don't propagate async context. Old ones may need AsyncResource.bind.
  • LogContext.set() with no store. Calling it outside a request silently does nothing.

The interceptor here subscribes inside run() for exactly this reason: subscribing outside would start the handler without the store. For background jobs, call run({ jobId }) at the job boundary.

8. Pitfalls

  • Building the message before checking the level: log.debug(JSON.stringify(big)) does the work even when DEBUG is off.
  • String concatenation instead of fields. Logs become unsearchable. Use a message plus structured fields.
  • Logging secrets: tokens, passwords, card numbers, full request bodies. Redact centrally, before any appender sees them.
  • An appender error that bubbles up. A full disk becomes 500s on every request.
  • Unbounded in-memory buffers. A log storm becomes an out-of-memory crash. Bound them, drop low levels, count the drops.
  • Dropping ERRORs under load, or not flushing on shutdown. You lose exactly the lines you need.
  • A global static logger configured at import time. Untestable and impossible to reconfigure. Use one instance owned by the app.
  • Passing requestId through every function signature. Use AsyncLocalStorage.
  • Computing effective levels by walking the hierarchy on every call without a cache. Or caching without clearing the cache on setLevel.

Say this

"One LogManager per app, provided as a Nest singleton, hands out named loggers. The same name returns the same instance, and a logger holds only its name. Levels are numeric and hierarchical by dotted name: the effective level is the nearest explicit ancestor's, cached, and the cache is cleared on any runtime change. A log call checks the level first, so a disabled line is one comparison and lazy messages are never built. An enabled call builds an immutable record with the message, per-call fields, and per-request context from AsyncLocalStorage, which an interceptor sets with the request id so it survives every await. The record passes through a chain of processors: redaction of secrets at any depth, filters, rate limits. Then it goes to every appender whose own threshold it meets: console with a formatter strategy, text or JSON lines; an in-memory ring buffer you can query; and a buffered decorator for slow sinks, bounded so it sheds low-level lines under load but never drops warnings or errors. An appender that fails is counted, never thrown. In production it writes JSON to stdout and a node agent ships it."
