Part B · System design (HLD)

An expense-sharing app for 50M users

The load is modest, and every group is small and independent. The design questions are: where balances live and how they stay exact to the paisa, how edits change balances that have already been settled, offline clients, and a user's total across hundreds of groups.

H1. Functional requirements

In scopeOut of scope

  • Add, edit and delete an expense: one or more payers; equal, exact, percent or shares splits
  • Balances per group, per friend, and overall. "Simplify debts".
  • Record a settlement, optionally paid through a UPI deep link
  • Activity feed, comments, receipt photos, notifications
  • Works offline on mobile and syncs later
  • Moving money ourselves. We record payments; UPI apps move the money.
  • OCR of receipts
  • Budgets and analytics

H3. Capacity estimation

Assumptions: 50M users, 5M DAU, 1 expense per DAU per day, 4 participants per expense, 10 group or balance views per DAU, 10% of expenses with a 500 KB receipt, 20M groups with 5 members on average. Peak is 5×.

Load is low and receipts dominate storage, so they go straight to object storage via presigned URLs and never pass through our servers. Because each group is small and independent, a single group never needs to scale. That makes group_id the obvious shard key.

H5. High-level design

{{sw-arch}}

One expense service owns groups, expenses and balances on a database sharded by group. Everything that spans groups (overall totals, the feed, notifications) is built from events.

  • Write path: validate membership → split engine computes exact shares → in one transaction: insert the expense, payer and share rows, apply balance deltas, bump the group version, write an outbox row.
  • Group read path: net balances come straight from the balances rows. The simplified view comes from Redis under the key (group, version), so it is invalidated by the version bump and computed again on a miss.
  • Friend-to-friend expenses outside any group are stored in an implicit two-person group. One code path, and it's still sharded by group.
  • Cross-group "you owe Asha ₹1,240 in total" is a projection keyed by user, updated from ExpenseAdded/Edited/Deleted and SettlementRecorded events.
{{sw-seq}}

An id generated on the client makes create idempotent. A version on update makes edits safe.

H6. Database design

Choice: Postgres, sharded by group_id. An expense, its shares and the balance deltas must change together. Everything a group screen needs is on one shard.

schema
  • Invariant per group and currency: Σ net_paise = 0. Checked when the delta is applied (deltas sum to zero by construction) and again by a nightly job.
  • "My groups" for a user spans shards. Keep a user_groups table on the user's shard, written by the membership events, or serve it from the summary store.

H7. Detailed component design

1 · Split engine

The same strategies as the LLD (equal, exact, percent in basis points, shares) with largest-remainder apportionment, so shares always add up to the amount exactly. The server is authoritative: the client sends the inputs (the percentages it typed), and the server computes and stores the paise. Multiple payers are just a second vector: each member's delta is paid − owed, and the deltas sum to zero.

2 · Balance maintenance by deltas

create / edit / delete are one operation

Edits never recompute history: they apply the difference. Settlements are expenses with a single payer and a single participant, so they flow through the same path. That answers S4 in the LLD: past settlements stay as they are, and the edit simply leaves a new non-zero balance.

3 · Debt simplification

  • Greedy over net balances: repeatedly match the largest creditor with the largest debtor. At most n − 1 payments, O(n log n). That's microseconds for real groups.
  • Finding the true minimum number of payments is NP-hard (it means finding zero-sum subsets). Greedy can be one payment worse: S2 in the LLD has a counterexample.
  • Cached on (group, version), so a busy group is computed once per change, not once per view.
  • A per-group setting "don't simplify" serves the pairwise view instead (who owes whom, exactly as recorded). That needs a pairwise(group, debtor, creditor) table maintained by the same deltas.

4 · Offline sync

  • The client keeps a queue of operations, each with its own UUID. Creates are idempotent by id, and edits carry the base version.
  • On reconnect, push the queue in order, then GET /sync?cursor. Each group has a change log ordered by version, and the cursor is a map of {groupId: version}.
  • Conflicts: edits to different expenses never conflict. An edit to the same expense from two devices gets 412, and the app shows both versions. Money is not something to merge silently with last-writer-wins.

H8. Interviewer questions and counters

Q1Store balances, or compute them from expenses on read?

Answer

Store them, updated by deltas in the same transaction as the expense. Reads outnumber writes 10:1, and some groups have thousands of expenses (S1 in the LLD). Expenses remain the source of truth: balances can always be rebuilt from them, and the nightly check does exactly that for a sample of groups.

Push-back: "Now you have two sources that can disagree."

Only if a write bypasses the single applyChange path, and the transaction makes them change together. The invariant check (Σ = 0, plus a rebuild-and-compare) catches bugs. The LLD derived balances on read because in memory that's free. Different constraints, different choice.

Q2Shard by group or by user?

Answer

By group. Every write touches exactly one group, and many users, so sharding by user would turn each expense into a transaction across shards. The group is the unit of consistency. The cost is that per-user views span groups, and those come from a projection that may lag by seconds.

Q3Why not let the client compute shares and balances? It has all the data.

Answer

Clients run different versions, round differently, and can be tampered with. Two phones computing a three-way split of ₹100 must agree on who pays the extra paisa. The client previews with the same algorithm, and the server decides and stores.

Q4Can you guarantee the minimum number of payments?

Answer

Not in general. Minimising transactions is NP-hard. For small groups (n ≤ 12 or so) you can search exhaustively: split the members into as many zero-sum subsets as possible, and the answer is n minus that count. That's affordable when computed once per version and cached. Above that, use greedy and accept that it may need an extra payment.

Push-back: "Greedy can make strangers pay each other."

True. Optionally restrict matches to pairs who share an expense, or show the pairwise view. That's a product choice, not an algorithm bug.

Q5Two people edit the same expense offline. Who wins?

Answer

The first to sync wins, and the second gets a 412 with the current version. The app asks the user to re-apply the change. Merging field by field (one fixed the description, the other the amount) is possible, since the fields are independent, but the amount and the split must never be merged automatically.

Q6Someone is in 300 groups. Their home screen total is slow.

Answer

It's never computed live: the summary projection stores, per user, the totals per friend and currency, updated incrementally from events. Reading it is one key lookup. If the projection ever drifts, rebuild it for that user from their groups' balances. That operation is idempotent and cheap.

Q7A trip abroad: expenses in EUR and INR. How do balances work?

Answer

Keep balances per currency (the key includes currency), so nothing is converted until someone chooses to. "Settle in INR" converts at the rate on the settlement date and records that rate. Converting each expense at its own date's rate is an option for users who want a single number, and the stored rate keeps it reproducible. S3 in the LLD covers the model change.

Q8Why have Kafka at all? It's a small app.

Answer

For the side effects that shouldn't be in the write transaction: the feed, push notifications, email digests, the summary projection. At this scale a Postgres outbox table polled by a worker is enough. Kafka becomes worthwhile when several independent consumers need replay, for example analytics. Start with the outbox; the event contract is the same either way.
