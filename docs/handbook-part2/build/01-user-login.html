Part B · System design (HLD)

Identity service for a 50M-user product

The LLD above is one auth module. Here it becomes an identity service that many other services trust, built to survive login floods, credential stuffing and a region going down.

H1. Functional requirements

In scopeOut of scope (say it out loud)

  • Log in, refresh, log out, log out everywhere, list and revoke devices

  • Roles; other services can check who the caller is and what roles they have
  • Audit trail of logins, failures and revocations

  • Profile management beyond name and email

What the numbers tell you

The data is small: a single Postgres primary holds it all. The real costs are CPU for hashing (30 cores just to log people in at peak) and verification traffic, which is why verification has to be local. The deny list is small enough to sit in every service's memory.

H5. High-level design

{{ul-arch}}

The auth service is the only component that can mint tokens. Every other service verifies them locally with the cached public key and a small set of revoked session ids that is pushed to it.

Request paths

  • Login: gateway (per-IP limit) → auth service → Redis (per-account failure count) → Postgres (user) → scrypt → new session row → signed access JWT + opaque refresh token.
  • Any other API call: the service verifies the JWT signature with the cached JWKS, checks exp, and checks sid against its in-memory deny set. There is no network hop, so auth adds no latency and can't take the call down.
  • Logout: the session is revoked in Postgres, revoked:{sid} is written to Redis with a TTL equal to the access-token lifetime and published on a channel. Every service adds the sid to its local deny set within a second or two.
  • Side effects (verification and reset emails, audit, fraud scoring) are driven by events written through an outbox, so login never waits on email.
{{ul-seq}}

Rotation is a compare-and-set on the stored hash. When an old token is presented again, the lookup finds it in the session's history, and that is how reuse is detected.

H6. Database design

Choice: Postgres. The data is relational and small (~30 GB), it needs unique constraints (email) and transactional compare-and-set (rotation), and the traffic is a few thousand writes a second at most. A key-value store buys scale this system doesn't need and gives up the constraints it does need.

schema
  • Failure counters and lockouts live in Redis (INCR fails:{email} with a 15-minute TTL), not in the users row. That keeps a hot write off the primary, and counters can be lost without harm: losing one only gives an attacker a few more guesses.
  • Retention: expired sessions and their history rows are deleted by a nightly job. login_events partitions are dropped after the retention period, so nothing has to be deleted row by row.
  • If it outgrows one primary: shard users by hash(email), because login looks users up by email, and keep a small user_id → shard directory. Sessions go on the same shard as their user.

H7. Detailed component design

1 · Token signing and key rotation

  • Access tokens are signed with EdDSA or RS256 using a private key that never leaves KMS. The auth service asks KMS to sign, or holds a short-lived data key. Verifiers only ever get the public key.
  • JWKS publishes two keys at a time, current and next. To rotate: publish next, wait longer than the JWKS cache TTL (5 min), start signing with it, and retire the old key after one access-token lifetime (15 min). Each token's kid header says which key to use.
  • Claims: iss, aud, sub, sid, roles, av (authz_version), iat, exp. Verifiers check aud, so a token issued for one service can't be replayed against another.

2 · Refresh rotation as compare-and-set

refresh, in one transaction

The WHERE refresh_hash = $old makes two concurrent refreshes safe without an application lock: Postgres row locking guarantees exactly one of them updates the row. The grace window for legitimate double refreshes (two tabs) is U3 in the LLD.

3 · Revocation propagation

  • On revoke: SET revoked:{sid} 1 PX 900000 plus PUBLISH revocations {sid, exp}.
  • Each service runs a small subscriber that adds the sid to an in-memory set and drops entries once their tokens have expired. At start-up it loads the current set with SCAN revoked:*, which holds about 10k keys.
  • If the subscriber disconnects, the service checks Redis per request until it has caught up again. If Redis is unreachable as well, it fails open for low-risk reads and fails closed for money movement. That policy is decided per endpoint, not left to chance.

Hashing runs in a separate worker pool with a bounded queue. When the queue is full, login returns 503 with Retry-After instead of letting a flood starve refresh and verification traffic on the same pods.

H8. Interviewer questions and counters

Q1Why JWTs at all? Opaque session ids in Redis are simpler and revocable.

Answer

With opaque ids, every API call in every service needs a network lookup. At 115k checks a second, that makes the session store a single point of failure for the whole company. A JWT moves verification into each service's own process. We keep only the part that can't be stateless, revocation, and it's a small set that is pushed to every service.

Push-back: "So you have state anyway. Why not go fully stateful?"

The state we keep is about 10k entries that change rarely. It's pushed to services, not queried, so if it's unavailable a service is a few seconds stale, not down. A session store would hold 20M entries and be on every request's critical path. For a single monolith with one database I'd happily use opaque sessions.

Q2Why not validate tokens once at the API gateway and trust everything behind it?

Answer

Gateway validation is a good first filter, and it's what I'd do for external traffic. But internal calls (service to service, async consumers acting on a user's behalf) don't pass through the gateway. If services trust a header such as X-User-Id, a single compromised pod can impersonate anyone.

Push-back: "Verifying in every service duplicates work."

Verification is one signature check, cheap and done locally. Put it in a shared library or the sidecar of a service mesh, so each team doesn't write its own.

Q3The users database is in Mumbai. You launch in Singapore. What changes?

Answer

Verification already works anywhere: JWKS is public and cached. Login and refresh need writes. Option A: give each user a home region, and route login and refresh there through a global directory keyed by email hash. That adds latency only to logins. Option B: run Postgres in every region with the user rows replicated, accepting a few seconds of lag for password changes. I'd pick A, because security writes (revocation, password reset) shouldn't be able to diverge between regions.

Push-back: "Mumbai is down. Can Singapore users log in?"

With A, users whose home is Mumbai can't log in or refresh, but their access tokens keep working everywhere until they expire, and users at home in Singapore are unaffected. If that's unacceptable, keep a read replica in each region and allow refresh in read-only mode: issue new access tokens but skip the rotation. That's a deliberate, temporary loss of reuse detection.

Q4A hard lockout after 5 failures lets an attacker lock out any user. Fix it.

Answer

Lock the combination rather than the account: count failures per (account, IP or device fingerprint), so the attacker's IP gets locked, not the user's laptop. Account-wide, use increasing delays and a CAPTCHA instead of a hard lock, and always let the user through with a password-reset link or a known-device cookie.

Push-back: "The attacker rotates through 10,000 IPs."

Then the per-IP counters never trigger, but the account-wide CAPTCHA and the global failure-ratio alarm do. Botnets can't easily solve CAPTCHAs at scale. Offering MFA turns a correct guess into a non-event.

Q5A login flood is burning all your CPU on scrypt. What do you do?

Answer

Reject before hashing: the IP and account limits, CAPTCHA and the WAF all run before the expensive step. The hash pool has a bounded queue and sheds load with 503. It runs on its own pods, so refresh (a cheap SHA-256) and verification (local) keep working. Autoscale on queue depth.

Push-back: "Just lower the scrypt cost then."

That makes offline cracking of a leaked database proportionally cheaper, and that's the threat the cost exists for. Tune it once, about 50 ms on the hardware you use, and handle load with capacity and admission control. The cost is stored in each hash, so it can go up later without forcing anyone to reset.

Q6Why is the refresh token opaque and not another JWT?

Answer

A refresh token is only ever checked by the auth service, which has the database anyway, so a self-contained token gains nothing. Being opaque means that what's stored is just a hash, and rotation and revocation are a single row update. A JWT refresh token would need a database check anyway to detect reuse.

Q7Access token lifetime: why 15 minutes? Why not 1 minute or 24 hours?

Answer

It bounds how long a stolen access token works if the deny list misses it, and it decides how much refresh traffic there is. At 1 minute, refreshes would rise 15× to about 35k/s at peak: real write load on Postgres. At 24 hours, a stolen token is valuable for a day. 15 minutes keeps refresh load at about 2.3k/s, and the deny list covers the gap.

Push-back: "Banking apps use 5 minutes."

Then make it a setting per client: the banking app uses 5 minutes and higher refresh load, the content app uses 30. The design doesn't change.

Q8How do you build "Sign in with Google" into this?

Answer

Add an identities(provider, subject, user_id) table. The OIDC callback verifies Google's ID token (signature, aud, nonce), finds or links the user, then creates our own session the same way password login does. Everything after that point (refresh, revocation, roles) is unchanged. Link to an existing account only if Google says the email is verified, and ask for the existing password the first time, so nobody takes over an account by registering its email with another provider.
