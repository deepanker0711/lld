Part B · System design (HLD)

A prepaid wallet holding real money

Correctness beats everything else: money is never created or destroyed, and every rupee can be traced. The hard parts are external rails that time out without saying what happened, hot merchant accounts, and transfers between users whose accounts sit on different shards.

H3. Capacity estimation

Assumptions: 50M wallets, 10M DAU, 20M transactions a day, 2 ledger entries per transaction on average (fees add more), 5 balance or statement reads per DAU. Peak is 5×, and festival spikes reach about 3k transactions a second.

What the numbers tell you

A few thousand writes a second fits one well-sized Postgres primary. Shard because of storage growth, blast radius and hot accounts, not raw throughput, and do it by account id. Statements are a read model so they never compete with posting.

H5. High-level design

{{wl-arch}}

The ledger service is the only code that can change a balance. Everything else (risk, the external rails, statements) sits around it and talks to it through posting requests or events.

  • Internal movement (P2P, merchant payment, fees, cashback) is synchronous: idempotency claim → risk and limits → one ledger posting → response.
  • External movement (top-up, payout) is a state machine in the money-movement service. The ledger records the internal side through a clearing account (for example "payouts in flight"), so money that is between us and the bank is always visible and balanced.
  • Reads: balances come from the account row on the primary. Statements come from a read model (Cassandra or a Postgres replica) built from TxnPosted events.
  • Reconciliation compares each rail's settlement file with the ledger every day. Any break (in the file but not in our ledger, or the other way round) opens a ticket.
{{wl-seq}}

The rule senior interviewers look for: a timeout is not a failure. Reversing a payout that actually succeeded gives money away.

H6. Database design

Choice: Postgres (or a distributed SQL database once you need cross-shard transactions). Posting needs multi-row ACID, check constraints and row locks. A ledger is relational and append-mostly, which is exactly what these databases are good at.

schema
  • balance_after on each entry makes statements and audits cheap, and lets you check any account at any point in time.
  • System accounts (clearing, fees) have allow_negative where it makes sense. "External world" is not an account with a balance row, so it never becomes a hot row.
  • The daily limit is a row updated in the same transaction (… SET outgoing = outgoing + $amt WHERE outgoing + $amt <= $limit), so two parallel transfers can't both slip under it.

H7. Detailed component design

1 · The posting engine

post(txn, from, to, amount): one transaction

2 · Idempotency that survives concurrency

  • Claim first: INSERT … (status IN_PROGRESS, fingerprint). A unique violation means the key has been seen before. If it's DONE with the same fingerprint, return the stored response. With a different fingerprint, 422. If it's still IN_PROGRESS, 409 "retry shortly".
  • For internal transfers the claim and the posting are in the same transaction, so a crash leaves nothing behind. For external legs the key row points at the transaction, and a retry returns its current status instead of starting over.
  • Keys expire after 7 days, longer than any client retry window.

3 · External money movement

Payout stateLedgerNext

PENDING / UNKNOWNno changeStatus enquiry with backoff, then the settlement file
SUCCEEDEDpayout-clearing D, bank-settlement CFinal
FAILED (definite)reversal: clearing D, user CFinal, user notified

Top-up is the mirror image: no ledger entry until the PSP confirms capture. Then topup-clearing D, user C.

4 · Sharding and cross-shard transfers

  • Shard accounts and ledger_entries by account id. A transfer between two accounts on the same shard is the local transaction above.
  • Across shards, run a two-step saga through a per-shard inter-shard clearing account. Step 1, on A's shard: A D, clearing C. Step 2, on B's shard: clearing D, B C. Each step is idempotent on txnId and driven by the outbox. If step 2 can't apply (B is frozen), a compensating step 1′ returns the money to A. Every shard balances at every moment, and the global sum of the clearing accounts is the money in flight.
  • The alternative is a distributed SQL database (Spanner, CockroachDB, YugabyteDB) that gives serializable cross-shard transactions. It's simpler code with higher write latency. Either is a defensible choice. Say which trade-off you're making.

5 · Hot accounts

A large merchant receiving 1,000 payments a second serialises on one row lock. Split the merchant into N sub-accounts and credit a random one. Read the balance as the sum, and sweep them together for settlement (W5 in the LLD has the code). Credits never fail on balance, so they don't need to see the total.

H8. Interviewer questions and counters

Q1Why a relational database? NoSQL scales better.

Answer

A posting changes at least two balances and inserts two entries atomically, with constraints. That's a multi-row transaction, which relational databases do natively. The load (a few thousand transactions a second) is well within their reach, and sharding by account handles growth.

Push-back: "DynamoDB has transactions too."

It does, with limits on size and throughput and no check constraints. You can build a ledger on it (some companies have), but you end up re-implementing what Postgres gives you. I'd choose it only for an existing AWS-native stack, and I'd say so.

Q2Which isolation level, and why not SERIALIZABLE?

Answer

READ COMMITTED plus explicit FOR UPDATE on the accounts involved, locked in a fixed order. The invariant ("balance never below zero") involves only rows we lock, so there's no write skew to worry about. SERIALIZABLE also works, but it aborts transactions under contention and the application has to retry them. It's the right choice when an invariant spans rows you don't lock.

Q3Why not make posting asynchronous: put transfers on Kafka and apply them in order?

Answer

A user sending money expects a definite yes or no now, and insufficient funds must be rejected at the moment of the request. A Kafka log partitioned by account does give ordering without locks, and some large ledgers work that way. The cost is that every response becomes "pending", and a transfer touches two partitions, which brings back the cross-shard problem. Keep posting synchronous, and use Kafka for what happens after.

Q4Isn't this event sourcing? Why keep balances?

Answer

The ledger is the event log, and the balance column is a projection kept in the same transaction, so it can never lag. Computing balances by summing entries on every read would be too slow for busy accounts (W2 in the LLD). A nightly job checks that balance = Σ credits − Σ debits for every account. A mismatch is an incident.

Q5How do you prove the system hasn't lost or created money?

Answer

Three checks. Per transaction: debits = credits, checked at write time and again by a streaming checker. Per account: balance = sum of its entries, checked nightly. Against the outside world: each rail's settlement file matches the clearing accounts, checked daily. Together they catch bugs, partial writes and errors at the bank's end.

Q6Active-active across two regions for availability?

Answer

Not for the same account. Two regions accepting debits on one balance can overdraw it. Instead: each account has a home region (active-active across accounts), synchronous replication within the region, and asynchronous replication to a standby region with a controlled failover. A cross-region transfer is a cross-shard saga.

Push-back: "Then a region outage stops those users."

Yes, until failover, which takes minutes and is rehearsed. That's the price of never double-spending. Reads (balance as of last sync, marked as possibly stale) can continue from the standby.

Q7The fraud model is slow (300 ms). Do you block transfers on it?

Answer

Use rule-based checks inline (velocity counters, limits, blocklists, all under 10 ms) and run the model asynchronously. For high-risk scores, act after the fact: freeze the account, hold the payout. A payout is the irreversible step, so that's where you can afford to wait for the model. A P2P transfer stays inside the system and can still be reversed.

Q8A user disputes a transaction from three years ago. Can you show what happened?

Answer

Yes. Entries are immutable and carry balance_after. The transaction row links to the idempotency key, the device and IP from the audit log, and the external reference. Old partitions are in cold storage but still queryable (for example Parquet files on S3 read with Athena). Corrections are always new transactions with reverses set, so history never changes.
