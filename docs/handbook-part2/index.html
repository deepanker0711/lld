Topic · LLD + HLD · src/modules/auth

User Login

Register with a hashed password, then log in to get a short-lived access token (a signed JWT) and a long-lived refresh token (an opaque random string, stored only as a hash). The refresh token rotates every time it's used, and using an old one again revokes the whole session. Logout works instantly because every request checks that the session is still active. Failed logins lock the account, and the lock is per email so parallel guesses can't get around it.

Core ruleAccess = JWT 15 min · Refresh = rotating, hash stored
ConcurrencyKeyedMutex per email (hashing is async)
PatternsStrategy (hasher), Guard, Decorator
Demo filerequests/auth.http

The session repository keeps two indexes. userId → sessions powers the "my devices" list and logout-all. refresh-token hash → session contains every hash the session has ever had, not just the current one. Tests (12)

  • Registration stores a salted hash and never returns it. Two registrations of the same email racing each other: exactly one succeeds.
  • A wrong password and an unknown email get the same 401.
  • 6 bad logins in parallel still trigger the lockout. After the 15 minutes pass (on the fake clock), login works again.
  • The access token expires at 15 minutes. A token with tampered claims, a token with alg=none, and a token signed with a different secret are all rejected.
  • Refresh rotation: reusing an old refresh token revokes the session, so the newest refresh token and access token are dead too.
  • Logging out kills that device's token but other devices keep working. Logout-all revokes every session. Revoking another user's session returns 404.

7. Senior follow-ups

U1Why not make the access token fully stateless and skip the session lookup?

Answer

You can, and many systems do. The trade-off is that a logged-out or stolen token keeps working until it expires. With a 15-minute lifetime that is often acceptable. When it isn't, keep the check but make it cheap. Revoking writes the session id to Redis with a TTL equal to the access token lifetime, and the guard does one EXISTS. The set only ever holds sessions revoked in the last 15 minutes, so it stays small.

Implementation change

revocation list
U2Ten services need to verify tokens. Do they all share the secret?

Answer

No. Switch to asymmetric signing (RS256 or EdDSA). Only the identity service holds the private key. Every other service verifies with the public key, which it fetches from a JWKS endpoint and caches. Each token carries a kid (key id) header, so you can rotate keys with no downtime: publish the new key, start signing with it, and retire the old key after the longest token lifetime has passed. A leaked verifier can't mint tokens.

Implementation change

jwks
U3A user has two tabs open. Both refresh at the same moment, and one gets logged out as "reuse".

Answer

That's the downside of strict rotation. You have two fixes. On the client, a single-flight refresh: one tab refreshes and the others wait for its result (via a BroadcastChannel, or a lock in a shared worker). On the server, a short grace window: when a token that was rotated less than about 10 seconds ago comes back, return the pair that was already issued instead of treating it as theft. Replays after the window are still treated as reuse. Keep the window short and tie it to the same session.

Implementation change

grace window
U4Where should the browser keep the tokens?

Answer

Keep the refresh token in an HttpOnly, Secure, SameSite=Strict cookie scoped to /auth/refresh. JavaScript can't read it, so an XSS attack can't steal it, and it's sent only to the refresh endpoint. Keep the access token in memory: a page reload calls refresh and gets a new one. Don't use localStorage, because any script injected into the page can read it. If the access token is also sent as a cookie, add CSRF protection, such as a double-submit token or SameSite plus checking Origin.

Implementation change

controller
U5An attacker tries one password against 10,000 accounts (credential stuffing).

Answer

The per-account lockout never triggers, because each account sees only one failure. Add limits along other dimensions: per IP and per subnet with a sliding window (the rate limiter from the Keka handbook), plus a global failure-rate alarm. Check new passwords against known breach lists (k-anonymity range queries against HaveIBeenPwned). When a login looks risky (new device, new country, IP on a block list), show a CAPTCHA or require an OTP instead of blocking outright. Also, lockout can be abused: an attacker can lock someone else out on purpose. So prefer increasing delays, or exempt known devices.

Implementation change

controller
U6Add "forgot password".

Answer

  • Request a reset: always return 202, whether or not the email exists. If it does, email a single-use token that is valid for 15 minutes. Store only its hash, just like a refresh token.
  • Confirm the reset: check the token's hash and expiry, set the new password, delete the token, and revoke every session. The point of a reset is to lock out anyone else who had access.
  • Abuse limits: rate-limit reset requests per email and per IP, so the endpoint can't be used to spam someone's inbox.

Implementation change

reset
U7Add OTP-based two-factor login.

Answer

Split login into two steps. Step 1: email and password are correct, so return a short-lived mfaToken (a signed token for "this user, step 1 done, valid 5 minutes"), not a session. Step 2: the client sends the mfaToken plus a TOTP code. The server checks the code against the user's TOTP secret, allowing ±1 time step for clock drift, and only then creates the session. Rate-limit step 2: a 6-digit code has only a million values. Offer one-time recovery codes, stored as hashes.

Implementation change

mfa
U8An admin removes a user's ADMIN role. Their existing access token still says ADMIN.

Answer

The token's roles are a snapshot taken when it was issued. There are three options, from least to most strict:

  • Accept up to 15 minutes of staleness. The next refresh picks up the new roles.
  • Bump a version number. Changing a user's roles increments their authzVersion. The token carries it, and the guard compares it with a cached value.
  • Revoke the user's sessions whenever their roles change.

For admin rights, use the version number or revocation. For everyday roles, staleness is usually fine.

8. Pitfalls

  • Hashing with SHA-256 or MD5. These are fast hashes, which is exactly what you don't want for passwords. Use a slow, salted one: scrypt, argon2 or bcrypt.
  • Comparing hashes or signatures with ===. Use timingSafeEqual.
  • Trusting the token header's alg. Pin it, or alg: none goes straight through.
  • Storing refresh tokens in plain text. Anyone who can read the database could then log in as anyone.
  • Different errors for "no such user" and "wrong password", or a fast path that skips hashing for unknown emails. Both leak which accounts exist.
  • Counting failures without a lock. Parallel guesses get past the lockout.
  • Refresh tokens that don't rotate, or rotation without reuse detection. A stolen token then lives forever.
  • Treating logout as client-side only (just delete the token). The token keeps working until it expires.
  • Returning passwordHash in any response, including admin lists.
  • Password rules on login. Users whose passwords predate the rules are locked out.
  • Returning 403 for a missing token. Unauthenticated is 401; authenticated but not allowed is 403.

60-second summary to say

Say this

"Users register with an email and a scrypt-hashed password with a random salt; the cost factor is stored inside the hash so it can be raised later. Login checks the password and creates a session: one per device. It returns a 15-minute HS256 access token carrying the user id, the session id and the roles, plus an opaque refresh token whose SHA-256 is all the server stores. Refreshing rotates that token. If an old one is ever presented again, someone has a copy, so the whole session is revoked. The guard verifies the signature and expiry, then checks the session is still active, so logout is immediate; at scale that check is a Redis revocation list. Login is serialised per email, so parallel guesses can't get past the five-failure lockout. Unknown emails and wrong passwords get the same answer in the same time. Roles are checked after authentication: 401 means who are you, 403 means you can't."

H5. High-level design

The auth service is the only component that can mint tokens. Every other service verifies them locally with the cached public key and a small set of revoked session ids that is pushed to it.

Request paths

  • Login: gateway (per-IP limit) → auth service → Redis (per-account failure count) → Postgres (user) → scrypt → new session row → signed access JWT + opaque refresh token.
  • Any other API call: the service verifies the JWT signature with the cached JWKS, checks exp, and checks sid against its in-memory deny set. There is no network hop, so auth adds no latency and can't take the call down.
  • Logout: the session is revoked in Postgres, revoked:{sid} is written to Redis with a TTL equal to the access-token lifetime and published on a channel. Every service adds the sid to its local deny set within a second or two.
  • Side effects (verification and reset emails, audit, fraud scoring) are driven by events written through an outbox, so login never waits on email.

Rotation is a compare-and-set on the stored hash. When an old token is presented again, the lookup finds it in the session's history, and that is how reuse is detected.

H6. Database design

Choice: Postgres. The data is relational and small (~30 GB), it needs unique constraints (email) and transactional compare-and-set (rotation), and the traffic is a few thousand writes a second at most. A key-value store buys scale this system doesn't need and gives up the constraints it does need.

schema
  • Failure counters and lockouts live in Redis (INCR fails:{email} with a 15-minute TTL), not in the users row. That keeps a hot write off the primary, and counters can be lost without harm: losing one only gives an attacker a few more guesses.
  • Retention: expired sessions and their history rows are deleted by a nightly job. login_events partitions are dropped after the retention period, so nothing has to be deleted row by row.
  • If it outgrows one primary: shard users by hash(email), because login looks users up by email, and keep a small user_id → shard directory. Sessions go on the same shard as their user.

H7. Detailed component design

1 · Token signing and key rotation

  • Access tokens are signed with EdDSA or RS256 using a private key that never leaves KMS. The auth service asks KMS to sign, or holds a short-lived data key. Verifiers only ever get the public key.
  • JWKS publishes two keys at a time, current and next. To rotate: publish next, wait longer than the JWKS cache TTL (5 min), start signing with it, and retire the old key after one access-token lifetime (15 min). Each token's kid header says which key to use.
  • Claims: iss, aud, sub, sid, roles, av (authz_version), iat, exp. Verifiers check aud, so a token issued for one service can't be replayed against another.

2 · Refresh rotation as compare-and-set

refresh, in one transaction

The WHERE refresh_hash = $old makes two concurrent refreshes safe without an application lock: Postgres row locking guarantees exactly one of them updates the row. The grace window for legitimate double refreshes (two tabs) is U3 in the LLD.

3 · Revocation propagation

  • On revoke: SET revoked:{sid} 1 PX 900000 plus PUBLISH revocations {sid, exp}.
  • Each service runs a small subscriber that adds the sid to an in-memory set and drops entries once their tokens have expired. At start-up it loads the current set with SCAN revoked:*, which holds about 10k keys.
  • If the subscriber disconnects, the service checks Redis per request until it has caught up again. If Redis is unreachable as well, it fails open for low-risk reads and fails closed for money movement. That policy is decided per endpoint, not left to chance.

H8. Interviewer questions and counters

Q1Why JWTs at all? Opaque session ids in Redis are simpler and revocable.

Answer

With opaque ids, every API call in every service needs a network lookup. At 115k checks a second, that makes the session store a single point of failure for the whole company. A JWT moves verification into each service's own process. We keep only the part that can't be stateless, revocation, and it's a small set that is pushed to every service.

Push-back: "So you have state anyway. Why not go fully stateful?"

The state we keep is about 10k entries that change rarely. It's pushed to services, not queried, so if it's unavailable a service is a few seconds stale, not down. A session store would hold 20M entries and be on every request's critical path. For a single monolith with one database I'd happily use opaque sessions.

Q2Why not validate tokens once at the API gateway and trust everything behind it?

Answer

Gateway validation is a good first filter, and it's what I'd do for external traffic. But internal calls (service to service, async consumers acting on a user's behalf) don't pass through the gateway. If services trust a header such as X-User-Id, a single compromised pod can impersonate anyone.

Push-back: "Verifying in every service duplicates work."

Verification is one signature check, cheap and done locally. Put it in a shared library or the sidecar of a service mesh, so each team doesn't write its own.

Q3The users database is in Mumbai. You launch in Singapore. What changes?

Answer

Verification already works anywhere: JWKS is public and cached. Login and refresh need writes. Option A: give each user a home region, and route login and refresh there through a global directory keyed by email hash. That adds latency only to logins. Option B: run Postgres in every region with the user rows replicated, accepting a few seconds of lag for password changes. I'd pick A, because security writes (revocation, password reset) shouldn't be able to diverge between regions.

Push-back: "Mumbai is down. Can Singapore users log in?"

With A, users whose home is Mumbai can't log in or refresh, but their access tokens keep working everywhere until they expire, and users at home in Singapore are unaffected. If that's unacceptable, keep a read replica in each region and allow refresh in read-only mode: issue new access tokens but skip the rotation. That's a deliberate, temporary loss of reuse detection.

Q4A hard lockout after 5 failures lets an attacker lock out any user. Fix it.

Answer

Lock the combination rather than the account: count failures per (account, IP or device fingerprint), so the attacker's IP gets locked, not the user's laptop. Account-wide, use increasing delays and a CAPTCHA instead of a hard lock, and always let the user through with a password-reset link or a known-device cookie.

Push-back: "The attacker rotates through 10,000 IPs."

Then the per-IP counters never trigger, but the account-wide CAPTCHA and the global failure-ratio alarm do. Botnets can't easily solve CAPTCHAs at scale. Offering MFA turns a correct guess into a non-event.

Q5A login flood is burning all your CPU on scrypt. What do you do?

Answer

Reject before hashing: the IP and account limits, CAPTCHA and the WAF all run before the expensive step. The hash pool has a bounded queue and sheds load with 503. It runs on its own pods, so refresh (a cheap SHA-256) and verification (local) keep working. Autoscale on queue depth.

Push-back: "Just lower the scrypt cost then."

That makes offline cracking of a leaked database proportionally cheaper, and that's the threat the cost exists for. Tune it once, about 50 ms on the hardware you use, and handle load with capacity and admission control. The cost is stored in each hash, so it can go up later without forcing anyone to reset.

Q6Why is the refresh token opaque and not another JWT?

Answer

A refresh token is only ever checked by the auth service, which has the database anyway, so a self-contained token gains nothing. Being opaque means that what's stored is just a hash, and rotation and revocation are a single row update. A JWT refresh token would need a database check anyway to detect reuse.

Q7Access token lifetime: why 15 minutes? Why not 1 minute or 24 hours?

Answer

It bounds how long a stolen access token works if the deny list misses it, and it decides how much refresh traffic there is. At 1 minute, refreshes would rise 15× to about 35k/s at peak: real write load on Postgres. At 24 hours, a stolen token is valuable for a day. 15 minutes keeps refresh load at about 2.3k/s, and the deny list covers the gap.

Push-back: "Banking apps use 5 minutes."

Then make it a setting per client: the banking app uses 5 minutes and higher refresh load, the content app uses 30. The design doesn't change.

Q8How do you build "Sign in with Google" into this?

Answer

Add an identities(provider, subject, user_id) table. The OIDC callback verifies Google's ID token (signature, aud, nonce), finds or links the user, then creates our own session the same way password login does. Everything after that point (refresh, revocation, roles) is unchanged. Link to an existing account only if Google says the email is verified, and ask for the existing password the first time, so nobody takes over an account by registering its email with another provider.

7. Senior follow-ups

C1Ten app servers. How do you stop overselling?

Answer

Move the "check and reserve" into the database, as one conditional statement per line: UPDATE … SET available = available − q WHERE id = $1 AND available ≥ q. If it affects 0 rows, that line is out of stock. Run all lines in one transaction so the reservation is all-or-nothing. The CHECK (available ≥ 0) constraint is the safety net if the code ever gets it wrong. For flash sales with one very hot product, row contention becomes the bottleneck. Then pre-split the stock into N bucket rows and take from a random bucket, or keep the counter in Redis with an atomic DECRBY and reconcile later.

C2The server crashes after charging but before confirming. Now what?

Answer

The order is stuck in PENDING_PAYMENT with stock reserved. Two things fix it:

  • A reconciler job: every minute, find PENDING_PAYMENT orders older than N minutes and ask the gateway for the payment's status by order id, which works because the order id was sent as the idempotency key. Captured → confirm. Not found or failed → release.
  • The gateway's webhook: it says "payment captured for order X". The same confirm runs, guarded by the state table so it happens only once.

Never release stock on a timer alone. A payment that was captured late would then have no stock to fulfil it.

Usually no. Carts are abandoned most of the time, so reserving on add would lock stock that never sells. There are two exceptions. Keys should also expire (after 24 hours, say) so the table doesn't grow forever.

C6Make checkout a saga: inventory, payment and orders are separate services.

Answer

The order service orchestrates the saga, in order:

  1. Create the order as PENDING.
  2. Ask inventory to reserve the stock.
  3. Ask payment to charge.
  4. On success, confirm, and inventory commits the reservation.

Each step has a compensation: release the reservation, refund the charge. Messages go through a transactional outbox, so "order PENDING" and the message "reserve stock" are committed together. Every consumer is idempotent, keyed by order id. Reservations expire on their own, so a stuck saga can't hold stock forever. Our single-process code already has the same shape: reserve, charge, then confirm or release.

The cart is priced live, so the cart page already shows the new price. The risk is a user who confirms a total they saw earlier. Have the client send expectedTotalPaise with checkout. If the server's total differs, return 409 "Prices changed" with the new totals, and don't charge. This guards against stale prices and coupon changes in one check.

8. Pitfalls

  • Floats for money. Use integer paise, and round tax once at the end.
  • Storing prices in the cart. A product's price changes and the cart still charges the old one.
  • Not copying prices into the order. A later price change rewrites past invoices.
  • Checking stock and then awaiting the payment before reserving. Two buyers both pay for one unit.
  • Reserving per item in a loop that can throw halfway. Validate every line first, then reserve all of them.
  • Keeping a coupon use after the payment fails. Single-use coupons get burnt by failed attempts.
  • Validating a coupon only when it's applied. It may have expired or run out by checkout time.
  • Clearing the cart before the payment succeeds. A declined card loses the user's cart.
  • No idempotency on checkout. A client retry after a timeout charges twice.
  • Applying a discount bigger than the subtotal, producing a negative total.

Say this

"Everything is integer paise. A cart stores only product ids and quantities and is priced live; an order copies names and prices in, so history never changes. Totals go subtotal, then the coupon discount, picked by a strategy per coupon kind with caps and minimums, then 18% tax on the discounted amount. Checkout needs an Idempotency-Key and runs under a per-user lock. H5. High-level design

One service per business area, each with its own database. Checkout orchestrates the saga. Every state change writes an outbox row in the same transaction, and a relay publishes it to Kafka.

  • Cart is a key-value document per user, read-heavy and cached. Prices are not stored in the cart: they are fetched live from pricing, which is cached for 60 seconds.
  • Checkout owns orders and the saga. It talks to inventory and payment synchronously for the steps the user waits on, and consumes payment events asynchronously.
  • Inventory is the only writer of stock. It keeps reservations with an expiry time, and a sweeper releases the expired ones.
  • Payment wraps the PSPs behind one interface (Strategy, as in the LLD), stores every webhook, and runs reconciliation.

The checkout saga. The user waits for steps 1–9 only. Confirmation is asynchronous, and every step can be retried safely because each one is keyed: the idempotency key, the reservation id, the order id sent to the PSP, and the PSP's event id.

4 · Late payment after the reservation expired

The user pays at 15:30 for a reservation that expired at 15:29, and the stock went to someone else. On PaymentSucceeded, checkout tries to commit. If the reservation is already RELEASED, it tries to re-reserve. If that succeeds the order is confirmed. If not, the order becomes CANCELLED with reason STOCK_EXPIRED, an automatic refund is issued, and the user is told. Prevention is better: make the reservation TTL longer than the PSP's payment window, and tell the PSP to expire the payment link before the reservation expires.

H8. Interviewer questions and counters

Q1Why a saga? Use a distributed transaction (2PC) across orders, inventory and payment.

Answer

The PSP is an external system that doesn't take part in our transactions, and payment can take minutes (UPI approval on the phone). 2PC would hold locks on stock rows for that long and block on the coordinator. A saga uses local transactions plus compensations: release stock, refund. Each step is idempotent and the orchestrator's state is in the orders table, so a crash simply resumes.

Push-back: "Sagas leave the system temporarily inconsistent."

Yes, and the states say so honestly: PENDING_PAYMENT with stock held. The user sees "payment pending", which is the truth. The invariants that matter (stock never negative, never charged twice) hold at every step, because they're enforced inside single-database transactions.

Q2Orchestration or choreography for the saga?

Answer

Orchestration, by checkout. The order flow is the core business process: one place should own its state machine, its timeouts and its compensations, and you can debug an order by reading one row. Choreography, where each service reacts to the others' events, is fine for side effects such as email, analytics and search indexing, and those consume OrderConfirmed.

Push-back: "The orchestrator is a single point of failure."

It's stateless pods over a replicated database. If a pod dies, another one picks the saga up from the order row and the outbox. It's a hotspot of logic, not of availability.

Q3Why reserve stock at checkout and not when the item is added to the cart?

Answer

Most carts are abandoned. Reserving at add-to-cart lets idle carts lock up stock, and a competitor could hoard it with bots. Reserving at checkout holds stock only for people who are actually paying, and only for 15 minutes. The cart shows "only 2 left" as information, not a promise. (The LLD's C3 covers this from the code side.)

Push-back: "The user loses the item at checkout. Bad experience."

For scarce items, do a short soft hold when the user enters checkout (the address step), and use a waiting room for drops. For ordinary stock the chance is tiny and the message is clear.

Q4Why not keep stock in Redis? It's faster.

Answer

Redis failover can lose acknowledged writes, because replication is asynchronous. With stock that means overselling or phantom stock. Keep Redis as an admission gate in front, and let the database row (with its CHECK constraint) have the final say.

Push-back: "Postgres can't do 1.7k/s on one row."

Correct. That's why the gate exists: once the tokens run out, the database stops seeing traffic. If the stock itself is large (say 50k units), split the counter across buckets.

Q5The webhook arrives before the client's checkout call has even returned. Problem?

Answer

It can happen with fast payment methods. The order row is committed (step 5) before the intent is created (step 6), so the webhook always finds the order. The confirm is a conditional update from PENDING_PAYMENT, so the order doesn't care which arrives first.

Q6How do you guarantee the event is published if the service crashes right after committing?

Answer

Transactional outbox. The event row is written in the same transaction as the state change. A relay (polling, or Debezium reading the database's change log) publishes it and marks it sent. Delivery is at least once, so consumers deduplicate on event id. Writing to the database and then calling Kafka separately ("dual write") loses events on crashes.

Q7Microservices from day one?

Answer

Not necessarily. A modular monolith with the same boundaries (cart, checkout, inventory, payment, each owning its own tables, talking through interfaces and an in-process outbox) gets 90% of the design benefit, and real transactions are a bonus. Split a module out when it needs independent scaling or its own team: inventory during sales, and payment for PCI compliance.

Q8The price changes between viewing the cart and paying. Which price is charged?

Answer

The price on the order snapshot, which is taken at checkout. Checkout sends the cart version it priced. If pricing has changed since, return 412 with the new totals, and the client shows "price updated, confirm?". After the order is created, its lines are frozen: the webhook confirms the stored total and never re-prices.

Movie Ticket Booking

Cinemas have screens, and each screen has a seat layout of rows by seat type. A show puts a movie on a screen at a time; shows on the same screen can't overlap, cleaning gap included. Booking is a two-step flow. First the user holds seats for 5 minutes, all or nothing. Then they confirm with a payment. Expired holds are released lazily, the moment anyone looks at them, so there are no timers. Before the payment call, the booking moves to CONFIRMING, so a slow payment can't lose the seats.

7. Senior follow-ups

M1A blockbuster opens. 50,000 people try to book the same show at 10:00.

Answer

  • Protect the database first: a waiting room (a virtual queue) admits users at the rate the system can handle.
  • Serve the seat map from a cache: Redis keeps one bitmap or hash per show, updated on every hold, so it's slightly stale but cheap to read.
  • Make holds atomic in Redis: one Lua script per hold does "check all seats are free, then set them with a TTL", which is all-or-nothing and expires by itself. The database records the confirmed bookings.
  • Keep the database rule as a backstop: the partial unique index makes a double booking impossible even if Redis and the database disagree.

Implementation change

hold.lua
M2Why lazy expiry instead of a timer per hold?

Answer

A timer per hold means thousands of timers, and all of them are lost on a restart. With lazy expiry, correctness only needs holdExpiresAt to be stored. Any read that finds a lapsed hold expires it. The downside is that expired holds linger in storage until something reads them. A periodic sweep (the job scheduler) can clean them up for reporting, but correctness never depends on it. In Redis, the key's TTL does the same job.

M3Don't let users leave a single empty seat between two booked ones.

Answer

This is a seat-selection rule, so it belongs in a validator strategy that runs before the hold. For each affected row, simulate the row with the requested seats taken. Reject if any free seat ends up with taken seats (or the aisle or row end) on both sides, unless that seat was already isolated before the request. Keep it per cinema or per screen: some chains enforce it, some don't.

no-orphan-seat rule
M4The payment gateway confirms by webhook, minutes later.

Answer

Confirm then becomes two steps. POST /confirm creates a payment intent, moves the booking to CONFIRMING (it can't lapse), and returns 202. The webhook "payment.succeeded {bookingId}" moves CONFIRMING to CONFIRMED, and "failed" releases the booking. The webhook handler must be idempotent, because providers retry: the state table already makes a second CONFIRMED a no-op or a 409. Add a deadline for CONFIRMING (say 15 minutes): a sweeper asks the gateway for the status and settles the booking either way.

M5Dynamic pricing: prices rise as the show fills up.

Answer

Add a new PricingStrategy that also reads the occupancy. The important part: the price is fixed when the hold is made, which the booking's quote already does. Otherwise the price could change between hold and pay. Show the price on the seat map with a note that prices may change until you hold.

M6How would you show the seat map live as other people pick seats?

Answer

Push changes instead of having clients poll. Each hold, confirm or release publishes seat.changed {showId, seats, status}. A WebSocket or SSE gateway subscribes per show and forwards the event to clients viewing that show. Clients load the full map once, then apply the changes. Send a version number with the full map so a client that missed events can tell and reload. At scale, fan out through Redis pub/sub, with one channel per show.

M7Cinema chains with many cities: how do you split the data?

Answer

  • Shard bookings and seat maps by showId. Every booking touches exactly one show, so no transaction ever spans shards.
  • Keep the catalogue (movies, cinemas, show times) apart. It's read-heavy and changes rarely, so it goes in a separate, cached, searchable store.
  • Build "my bookings" separately. The question is per user, not per show, so keep a read model keyed by userId and fed by booking events.

8. Pitfalls

  • Checking and occupying seats one at a time. A failure on the third seat leaves the first two held. Check every seat first, then occupy them all together.
  • A status field on every seat, kept in sync with the bookings by hand. Derive the status from the owner booking.
  • Timers for every hold. They're lost on restart and don't scale. Expire holds lazily.
  • Letting a hold lapse while its payment is in flight. The seat goes to two people.
  • Repricing at payment time. The user pays a different amount from the one they saw.
  • Working out the weekday in UTC. A Friday-night show in IST gets priced as Thursday.
  • Show overlap that ignores the cleaning gap, or uses <= where it should be <. Shows that touch exactly at the boundary are fine.
  • Allowing a refund right up to the start time. Seats can't be resold in the last minutes. Use a cut-off.

60-second summary to say

Say this

"Screens have a layout of rows by seat type, expanded into seats once. A show places a movie on a screen, and shows can't overlap including the cleaning gap; in Postgres that's an exclusion constraint. Seat state isn't stored per seat: there's a map from show and seat to the booking that owns it, and the seat's status comes from that booking. Booking is hold, then pay. A hold checks every requested seat and takes them all in one synchronous block, so it's all-or-nothing and two users can't get the same seat; in a database that's inserting the seat rows under a partial unique index. Holds last five minutes and expire lazily: whoever reads a lapsed hold releases it, so there are no timers. Confirm locks per booking and moves the booking to CONFIRMING before the payment await, so a slow payment can't lose the seats; a decline goes back to HELD if there's time left. Price is a strategy, quoted at hold time, so the user pays what they saw."

H5. High-level design

Browsing is served from search and cache. Show inventory is the only writer of seat state. Seat changes go out as events, and a push service fans them out to everyone viewing that show.

  • Read path: movies and shows come from Elasticsearch behind a CDN. The seat layout is immutable per screen and cached for days. The status bitmap is cached in Redis per show and updated from SeatsChanged events.
  • Write path: holds go to show inventory, which runs one conditional update per request on the show's partition. Booking orchestrates payment and the final state, just like the checkout saga.
  • Hot shows: when demand for a show crosses a threshold, the gateway's waiting room lets users in at a rate the partition can serve (H7.3).
  • Partner cinemas: chains with their own box-office systems sync both ways through an adapter. Counter sales come in as holds from a "box office" channel, so there is still one writer of seat state.

CONFIRMING fences the hold before money moves. The sweeper skips CONFIRMING seats, so a slow payment can't lose them, and a dead payment can't keep them forever.

H6. Database design

Choice: Postgres, partitioned by show. Seat state needs multi-row atomic updates and constraints. Each show's seats are a few hundred rows that are always accessed together, so show_id is the natural shard key. Catalog data is replicated to Elasticsearch for search.

  • The exclusion constraint is the database form of the LLD's overlap check: two admins scheduling at once can't both succeed.

H7. Detailed component design

1 · The hold: one statement, all or nothing

hold

Postgres locks each matching row, so two overlapping holds serialise on the shared seats and the second sees them as taken. Lock order is not a deadlock risk here because each statement locks rows in index order. Holding nothing across a network call keeps lock time to milliseconds.

2 · Hold expiry

  • Correctness is lazy: an expired hold counts as free in the WHERE clause above, so the next hold simply takes the seat. No timer has to fire on time.
  • Cleanliness is a sweeper: every 30 s, UPDATE … SET status = 'FREE' WHERE status = 'HELD' AND hold_expires_at < now(), which emits SeatsChanged so seat maps turn green again.
  • CONFIRMING is skipped by both, until hold_expires_at + payment window. After that, the reconciler asks the PSP before releasing anything.

3 · Hot-show admission (waiting room)

  • Demand per show is measured at the gateway. Above a threshold, new visitors to that show get a signed queue ticket with a position, and an admitter lets in N users a second (for example 200/s), sized to what the partition can serve.
  • Admitted users get a short-lived token that the hold endpoint requires. Without a token, the request gets 429 at the edge and never reaches the database.
  • This also gives fairness: requests are served in arrival order, instead of rewarding whoever retries fastest.

4 · Live seat map fan-out

  • Show inventory publishes SeatsChanged {show, version, seats} through its outbox. A push tier subscribes per show (Redis pub/sub, or a Kafka consumer that routes by show) and forwards to every socket watching that show.
  • Clients apply deltas in version order. On a gap or a reconnect they fetch the snapshot again with GET /seats. This is a classic snapshot-plus-deltas design.
  • For a hot show, batch the updates every 500 ms. 100k viewers × 50 updates a second unbatched is 5M messages a second. Batched, it's 200k.

H8. Interviewer questions and counters

Q1Why lock seats in the database? Redis with SETNX is much faster.

Answer

The database is the source of truth, and a single conditional update is atomic across all the seats with no extra moving parts. Average load is 50 holds a second. Redis (the Lua script in M1) is a valid choice for hot shows. But then you have two stores that must agree when the booking is confirmed, and if Redis loses a key on failover, the same seat can be sold twice.

Push-back: "Opening night, 1.7k holds/s on one show."

Most of those fail fast on a couple of hundred rows, and the waiting room caps the arrival rate anyway. If measurements show the partition still struggles, add Redis as a pre-filter: reject requests for seats Redis already shows as held, and let the database decide the rest.

Q2Optimistic or pessimistic locking?

Answer

The hold statement is effectively optimistic, because the condition is checked in the update itself and nothing is locked while the user thinks. Row locks last only for the duration of the statement. A SELECT … FOR UPDATE followed by application logic and then an update would hold locks across a round trip and serialise everyone on popular seats.

Q3Why 5 minutes for a hold? Why not 15?

Answer

It's a trade-off between letting slow payers finish and keeping seats from being locked by people who walked away. Seats are scarce and demand is spiky, so it's short, unlike a shopping cart. CONFIRMING then extends the hold only for users who actually started paying. Measure abandonment and tune it per channel.

Push-back: "Bots hold seats and let them expire, over and over."

Rate-limit holds per user and device, require a login before holding, cap active holds at one per user per show, and add a short cool-down after an expiry.

Q4Payment succeeds but the seats were already released and resold.

Answer

CONFIRMING is designed to stop this from happening at all. If it still happens (for example a very late webhook after the grace period), the booking becomes FAILED_SEATS_LOST, an automatic refund is issued, and the user is told straight away. Optionally, offer the nearest free seats of the same type. The PSP payment link expiring before the grace period ends is what keeps this rare.

Q5Why not put every booking request on a queue partitioned by show and process them serially?

Answer

It works, and it removes lock contention: a single consumer per show applies holds in order. The costs are a synchronous user action turned into async (the client has to poll or wait for a push to learn whether it got the seats), and queue lag on hot shows when users need an answer within a second. A conditional update gives the same serialisation per row with an immediate answer. I'd use the queue only if the database truly couldn't keep up after the waiting room.

Q6How do you keep the seat map fresh for 100k viewers without hammering the database?

Answer

Viewers never read the database: snapshots come from the Redis bitmap and changes are pushed (H7.4). Holds are the only database writes, and each produces one event, however many people are watching.

Push-back: "WebSockets are expensive. Why not poll?"

Polling every 2 s × 100k viewers is 50k requests a second that mostly return "no change". With ETags they're cheap, and that's an acceptable fallback (and what mobile clients on bad networks use). A push connection is idle almost all the time, which costs less at this scale.

Q7The cinema's own box office sells seats too. Who is the source of truth?

Answer

One system has to own each show's inventory. Usually that's the cinema chain's system, and we are a sales channel with an allocation or a live API. If they own it, our hold becomes a call to their API with a timeout, and we show "pending" when they're slow. If we own it, their counter becomes another client of our hold API. The bad option is two sources syncing after the fact, because the same seat then gets sold twice.

Wallet System

A prepaid wallet with a double-entry ledger. Every movement of money writes a DEBIT and a CREDIT of the same amount, and the ledger is append-only. A wallet's balance is a cached sum of its entries, and a reconcile endpoint proves the two agree. There are three operations: top-up (card to wallet), transfer (wallet to wallet) and withdrawal (wallet to bank). Every one requires an Idempotency-Key, stored together with a fingerprint of the request. Operations that call the outside world create their transaction record before the await, which makes retries safe.

7. Senior follow-ups

W1Two servers process transfers from the same wallet at the same moment.

Answer

Use one database transaction per transfer. It locks both wallet rows in a fixed order (by id, so two opposite transfers can't deadlock), checks the balance, updates both balances and inserts both entries. CHECK (balance ≥ 0) is the backstop. The other option is optimistic locking: UPDATE … SET balance = balance − x, version = version + 1 WHERE id = $1 AND version = $v AND balance ≥ x, retrying when it affects 0 rows. That scales better when conflicts are rare. The unique (initiator, idempotency_key) index stops a duplicate even if two servers receive the same retry.

Implementation change

TypeORM transfer
W2Why keep a cached balance at all? Sum the ledger.

Answer

Summing millions of entries on every balance check and every transfer is too slow, and "check balance, then debit" needs a single row to lock. The ledger is the source of truth and the balance is a cache, kept correct because only post() writes it, in the same transaction as the entries. Reconciliation (nightly, plus spot checks) recomputes from the ledger and alerts on any difference. For very old accounts, store a snapshot (balance as of entry N) so a reconcile only sums the entries after N.

W3The bank payout times out. Did the money leave or not?

Answer

A timeout means you don't know, so it isn't a failure. Reversing would give the user money that may already have reached their bank. Keep the transaction PENDING with the wallet already debited, and settle it later. Options: poll the bank's status API using the transaction id (sent to the bank as the idempotency key), wait for the bank's webhook, or read the bank's end-of-day settlement file. Reverse only on a definite rejection. This module reverses on any error, which is fine for a fake rail. In production, split RailsDeclinedError (definite) from RailsTimeoutError (unknown).

multi-leg post
W5A celebrity's wallet receives 1,000 transfers per second. One row lock is the bottleneck.

Answer

Only debits need the balance check. Credits can't overdraw, so they don't need the lock. Options:

  • Append credits only. Insert the entries without updating the balance row, and roll the pending credits into the balance every few seconds. The available balance is then the stored balance plus the credits not yet rolled in.
  • Shard the hot wallet into sub-accounts. Credits go to a random sub-account; a debit draws from one sub-account and may need to borrow from the others.
  • Queue per wallet. Put a single-writer queue in front of each wallet (Kafka partitioned by wallet id), so there is no lock at all.
W6A user disputes a transfer: "I never sent that."

Answer

The ledger answers the question: entries, transaction id, time, device and IP (store them on the transaction), and the auth session that started it. If the dispute is upheld, the fix is a new reversing transaction that is linked to the original (reversesTxnId). Never edit or delete the original entries. If the recipient has already spent the money, the reversal can push their balance negative. That's a business decision, and it's why some systems hold incoming funds for a while first.

8. Pitfalls

  • Floats for money, or mixing rupees and paise. Use integer paise everywhere.
  • wallet.balance += x in several places. Have exactly one function that writes entries and balance together.
  • Editing or deleting ledger entries to "fix" mistakes. Post reversing entries instead.
  • Single-entry ledgers (one row per transfer). You can't prove where the money went, or that none was created.
  • Creating the transaction record after calling the payment gateway. A retry charges twice.
  • Same Idempotency-Key with a different body silently accepted.
  • Checking the balance, then awaiting something, then debiting. Two withdrawals overdraw the account.
  • Reversing a payout on a timeout. The user is paid twice.
  • Locking two wallets in request order. A→B and B→A at the same moment deadlock. Lock in id order.
  • Computing "today" in UTC for daily limits, when users expect the day to reset at midnight IST.

60-second summary to say

Say this

"Money is integer paise in a double-entry ledger: every movement writes a debit and a credit of the same amount under one transaction, entries are append-only, and an external system account is the other side of top-ups and payouts, so the whole ledger always sums to zero; there's an endpoint that proves it. Each wallet's balance is a cache of its entries, written only by one post function, and reconcile compares the two. Every operation takes an Idempotency-Key scoped to the wallet, with a fingerprint of the body: same key and body replays, a different body is 422. Transfers are one synchronous block: validate, check limits and funds, write two entries. Anything that calls the outside world records a PENDING transaction before the await, so retries don't double-charge. Withdrawals debit first and compensate with a reversing entry if the bank definitively rejects. Across servers, a transfer locks both wallet rows in id order with a CHECK against overdraft and a unique key for idempotency."

H5. High-level design

The ledger service is the only code that can change a balance. Everything else (risk, the external rails, statements) sits around it and talks to it through posting requests or events.

  • Internal movement (P2P, merchant payment, fees, cashback) is synchronous: idempotency claim → risk and limits → one ledger posting → response.
  • External movement (top-up, payout) is a state machine in the money-movement service. The ledger records the internal side through a clearing account (for example "payouts in flight"), so money that is between us and the bank is always visible and balanced.
  • Reads: balances come from the account row on the primary. Statements come from a read model (Cassandra or a Postgres replica) built from TxnPosted events.
  • Reconciliation compares each rail's settlement file with the ledger every day. Any break (in the file but not in our ledger, or the other way round) opens a ticket.

The rule senior interviewers look for: a timeout is not a failure. Reversing a payout that actually succeeded gives money away.

H6. Database design

Choice: Postgres (or a distributed SQL database once you need cross-shard transactions). Posting needs multi-row ACID, check constraints and row locks. A ledger is relational and append-mostly, which is exactly what these databases are good at.

schema
  • balance_after on each entry makes statements and audits cheap, and lets you check any account at any point in time.
  • System accounts (clearing, fees) have allow_negative where it makes sense. "External world" is not an account with a balance row, so it never becomes a hot row.
  • The daily limit is a row updated in the same transaction (… SET outgoing = outgoing + $amt WHERE outgoing + $amt <= $limit), so two parallel transfers can't both slip under it.

2 · Idempotency that survives concurrency

  • Claim first: INSERT … (status IN_PROGRESS, fingerprint). A unique violation means the key has been seen before. If it's DONE with the same fingerprint, return the stored response. With a different fingerprint, 422. If it's still IN_PROGRESS, 409 "retry shortly".

4 · Sharding and cross-shard transfers

  • Shard accounts and ledger_entries by account id. A transfer between two accounts on the same shard is the local transaction above.
  • Across shards, run a two-step saga through a per-shard inter-shard clearing account. Step 1, on A's shard: A D, clearing C. Step 2, on B's shard: clearing D, B C. Each step is idempotent on txnId and driven by the outbox. If step 2 can't apply (B is frozen), a compensating step 1′ returns the money to A. Every shard balances at every moment, and the global sum of the clearing accounts is the money in flight.
  • The alternative is a distributed SQL database (Spanner, CockroachDB, YugabyteDB) that gives serializable cross-shard transactions. It's simpler code with higher write latency. Either is a defensible choice. Say which trade-off you're making.

5 · Hot accounts

A large merchant receiving 1,000 payments a second serialises on one row lock. Split the merchant into N sub-accounts and credit a random one. Read the balance as the sum, and sweep them together for settlement (W5 in the LLD has the code). Credits never fail on balance, so they don't need to see the total.

H8. Interviewer questions and counters

Q1Why a relational database? NoSQL scales better.

Answer

A posting changes at least two balances and inserts two entries atomically, with constraints. That's a multi-row transaction, which relational databases do natively. The load (a few thousand transactions a second) is well within their reach, and sharding by account handles growth.

Push-back: "DynamoDB has transactions too."

It does, with limits on size and throughput and no check constraints. You can build a ledger on it (some companies have), but you end up re-implementing what Postgres gives you. I'd choose it only for an existing AWS-native stack, and I'd say so.

Q2Which isolation level, and why not SERIALIZABLE?

Answer

READ COMMITTED plus explicit FOR UPDATE on the accounts involved, locked in a fixed order. The invariant ("balance never below zero") involves only rows we lock, so there's no write skew to worry about. SERIALIZABLE also works, but it aborts transactions under contention and the application has to retry them. It's the right choice when an invariant spans rows you don't lock.

Q3Why not make posting asynchronous: put transfers on Kafka and apply them in order?

Answer

A user sending money expects a definite yes or no now, and insufficient funds must be rejected at the moment of the request. A Kafka log partitioned by account does give ordering without locks, and some large ledgers work that way. The cost is that every response becomes "pending", and a transfer touches two partitions, which brings back the cross-shard problem. Keep posting synchronous, and use Kafka for what happens after.

Q4Isn't this event sourcing? Why keep balances?

Answer

The ledger is the event log, and the balance column is a projection kept in the same transaction, so it can never lag. Computing balances by summing entries on every read would be too slow for busy accounts (W2 in the LLD). A nightly job checks that balance = Σ credits − Σ debits for every account. A mismatch is an incident.

Q5How do you prove the system hasn't lost or created money?

Answer

Three checks. Per transaction: debits = credits, checked at write time and again by a streaming checker. Per account: balance = sum of its entries, checked nightly. Against the outside world: each rail's settlement file matches the clearing accounts, checked daily. Together they catch bugs, partial writes and errors at the bank's end.

Q6Active-active across two regions for availability?

Answer

Not for the same account. Two regions accepting debits on one balance can overdraw it. Instead: each account has a home region (active-active across accounts), synchronous replication within the region, and asynchronous replication to a standby region with a controlled failover. A cross-region transfer is a cross-shard saga.

Push-back: "Then a region outage stops those users."

Yes, until failover, which takes minutes and is rehearsed. That's the price of never double-spending. Reads (balance as of last sync, marked as possibly stale) can continue from the standby.

Q7The fraud model is slow (300 ms). Do you block transfers on it?

Answer

Use rule-based checks inline (velocity counters, limits, blocklists, all under 10 ms) and run the model asynchronously. For high-risk scores, act after the fact: freeze the account, hold the payout. A payout is the irreversible step, so that's where you can afford to wait for the model. A P2P transfer stays inside the system and can still be reversed.

Q8A user disputes a transaction from three years ago. Can you show what happened?

Answer

Yes. Entries are immutable and carry balance_after. The transaction row links to the idempotency key, the device and IP from the audit log, and the external reference. Old partitions are in cold storage but still queryable (for example Parquet files on S3 read with Athena). Corrections are always new transactions with reverses set, so history never changes.

S1A group has 50,000 expenses. Recomputing balances on every read is slow.

Answer

Keep a running balance table (group, member) → net, updated in the same transaction as each expense insert, delete and settlement. Each change only adds or subtracts that event's deltas, so it's O(participants), not O(history). The derived calculation stays as the reconciliation check. Pairwise needs a (group, a, b) table, still updated by deltas. Simplify is O(n log n) over members, not expenses, so it can still run on every read.

S2Is greedy optimal? Can you do fewer payments?

Answer

Greedy guarantees at most n − 1 payments, but not the minimum. The minimum is n minus the largest number of disjoint zero-sum subgroups. Example: balances {+3, +2, +2, −3, −4}. The optimum is 3 payments ({+3, −3} and {+2, +2, −4}), but greedy matches +3 with −4 first and ends up making 4. Finding the true minimum is NP-hard, because it contains subset-sum. For small groups (≤ 12 people) you can find it exactly with a bitmask dynamic programme over subsets: the cost is 2ⁿ, still tiny at that size. Splitwise-style apps use greedy or a heuristic, because 2 payments vs 3 rarely matters to users.

Don't convert at entry time and throw the original away. Rates move, and the record should show what really happened.

S4Someone edits an expense from ₹900 to ₹1200. What happens to past settlements?

Answer

Balances are derived, so editing the expense (recomputing its shares) is enough: everything downstream updates. Settlements stay as they were, because they're real payments that happened. Someone who had settled may now owe again, and the balances show it. Keep an audit trail (expense versions: who changed what, when), and notify the other participants. Editing in place is fine here, unlike a payment ledger, because these records describe what people owe each other, not money that moved.

S5Two people add expenses to the same group at the same moment.

Answer

Nothing conflicts: expenses are appended, and balances are a sum. This is a deliberate strength of the design. With the running-balance table (S1), concurrent updates use net = net + delta (an atomic increment), never read-modify-write, so there's no lost update. The only check that needs care is settle, which reads the balance to cap the amount. Two settlements racing could each pass. Lock the group's balance rows (SELECT … FOR UPDATE) for a settlement, or accept the overpay and let the balance go positive the other way, since it's a recorded real-world payment.

S6Recurring expenses: rent split every month.

Answer

Store a template (payer, amount, split, cron rule). A scheduled job creates the real expense each period. That's the job scheduler's recurring job, with an idempotency key of (templateId, period) so a retried run doesn't add rent twice. Editing the template changes future months only.

8. Pitfalls

  • Dividing in floats (1000 / 3 = 333.333…) and rounding each share. The shares stop adding up to the total.
  • Rounding every share up or down the same way. You end up a paisa short or over. Use largest remainder.
  • Storing balances and editing them by hand. They drift, and deleting an expense becomes a puzzle.
  • Always including the payer in the split. "I paid for your ticket" then becomes a 50/50 split.
  • Allowing a settlement larger than the debt, which silently turns into a debt the other way.
  • Letting members leave with an open balance. The money disappears.
  • Calling greedy "optimal" in the interview. Say "at most n − 1, the true minimum is NP-hard."
  • Comparing percentages as floats (33.33 + 33.33 + 33.34 ≠ 100 in floating point). Convert to basis points first.

H7. Detailed component design

1 · Split engine

The same strategies as the LLD (equal, exact, percent in basis points, shares) with largest-remainder apportionment, so shares always add up to the amount exactly. The server is authoritative: the client sends the inputs (the percentages it typed), and the server computes and stores the paise. Multiple payers are just a second vector: each member's delta is paid − owed, and the deltas sum to zero.

2 · Balance maintenance by deltas

create / edit / delete are one operation

Edits never recompute history: they apply the difference. Settlements are expenses with a single payer and a single participant, so they flow through the same path. That answers S4 in the LLD: past settlements stay as they are, and the edit simply leaves a new non-zero balance.

3 · Debt simplification

  • Greedy over net balances: repeatedly match the largest creditor with the largest debtor. At most n − 1 payments, O(n log n). That's microseconds for real groups.
  • Finding the true minimum number of payments is NP-hard (it means finding zero-sum subsets). Greedy can be one payment worse: S2 in the LLD has a counterexample.
  • Cached on (group, version), so a busy group is computed once per change, not once per view.
  • A per-group setting "don't simplify" serves the pairwise view instead (who owes whom, exactly as recorded). That needs a pairwise(group, debtor, creditor) table maintained by the same deltas.

4 · Offline sync

  • The client keeps a queue of operations, each with its own UUID. Creates are idempotent by id, and edits carry the base version.
  • On reconnect, push the queue in order, then GET /sync?cursor. Each group has a change log ordered by version, and the cursor is a map of {groupId: version}.
  • Conflicts: edits to different expenses never conflict. An edit to the same expense from two devices gets 412, and the app shows both versions. Money is not something to merge silently with last-writer-wins.

H8. Interviewer questions and counters

Q1Store balances, or compute them from expenses on read?

Answer

Store them, updated by deltas in the same transaction as the expense. Reads outnumber writes 10:1, and some groups have thousands of expenses (S1 in the LLD). Expenses remain the source of truth: balances can always be rebuilt from them, and the nightly check does exactly that for a sample of groups.

Push-back: "Now you have two sources that can disagree."

Only if a write bypasses the single applyChange path, and the transaction makes them change together. The invariant check (Σ = 0, plus a rebuild-and-compare) catches bugs. The LLD derived balances on read because in memory that's free. Different constraints, different choice.

Q2Shard by group or by user?

Answer

By group. Every write touches exactly one group, and many users, so sharding by user would turn each expense into a transaction across shards. The group is the unit of consistency. The cost is that per-user views span groups, and those come from a projection that may lag by seconds.

Q3Why not let the client compute shares and balances? It has all the data.

Answer

Clients run different versions, round differently, and can be tampered with. Two phones computing a three-way split of ₹100 must agree on who pays the extra paisa. The client previews with the same algorithm, and the server decides and stores.

Q4Can you guarantee the minimum number of payments?

Answer

Not in general. Minimising transactions is NP-hard. For small groups (n ≤ 12 or so) you can search exhaustively: split the members into as many zero-sum subsets as possible, and the answer is n minus that count. That's affordable when computed once per version and cached. Above that, use greedy and accept that it may need an extra payment.

Push-back: "Greedy can make strangers pay each other."

True. Optionally restrict matches to pairs who share an expense, or show the pairwise view. That's a product choice, not an algorithm bug.

Q5Two people edit the same expense offline. Who wins?

Answer

The first to sync wins, and the second gets a 412 with the current version. The app asks the user to re-apply the change. Merging field by field (one fixed the description, the other the amount) is possible, since the fields are independent, but the amount and the split must never be merged automatically.

Q6Someone is in 300 groups. Their home screen total is slow.

Answer

It's never computed live: the summary projection stores, per user, the totals per friend and currency, updated incrementally from events. Reading it is one key lookup. If the projection ever drifts, rebuild it for that user from their groups' balances. That operation is idempotent and cheap.

Q7A trip abroad: expenses in EUR and INR. How do balances work?

Answer

Keep balances per currency (the key includes currency), so nothing is converted until someone chooses to. "Settle in INR" converts at the rate on the settlement date and records that rate. Converting each expense at its own date's rate is an option for users who want a single number, and the stored rate keeps it reproducible. S3 in the LLD covers the model change.

Q8Why have Kafka at all? It's a small app.

Answer

For the side effects that shouldn't be in the write transaction: the feed, push notifications, email digests, the summary projection. At this scale a Postgres outbox table polled by a worker is enough. Kafka becomes worthwhile when several independent consumers need replay, for example analytics. Start with the outbox; the event contract is the same either way.

F110,000 agents in a city send their location every 5 seconds. "Nearest free agent" is a scan.

Answer

Use a geospatial index, and keep agent locations out of the main database. Redis GEOADD agents:free {lng} {lat} {agentId} on every ping, and GEOSEARCH … BYRADIUS 5 km ASC COUNT 10 for candidates. Store only free agents in that set: assignment removes the agent atomically (ZREM, where a return of 1 means you got them), and becoming free adds them back. An alternative is H3 or geohash cells: look in the pickup's cell and its neighbours. Location pings are fire-and-forget; losing one is fine.

F2Nearest-first isn't the best assignment. What would you do instead?

Answer

Greedy nearest-first is locally optimal but globally poor. Better options:

  • Batch assignment. Collect orders and free agents over a short window (10–30 s), then solve the assignment problem: the Hungarian algorithm, or a min-cost flow, with costs such as pickup ETA + food-ready time + delivery ETA.
  • Stacking. Let one agent carry two orders from the same restaurant going the same way.
  • Assign before the food is ready. Hand the order out so the agent arrives when the kitchen finishes, not at the moment it's accepted.

All of these slot in behind AgentAssignmentStrategy, taking batches instead of single orders.

F3The agent rejects the assignment, or doesn't respond.

Answer

Add an offer step. Assignment creates an offer with a 30-second deadline, and the agent is RESERVED rather than BUSY. If the agent accepts, they become BUSY. If they reject or time out, the next candidate gets an offer and the agent goes back to AVAILABLE. Keep the order's rejected agents in a list so the same agent isn't asked again. The deadline is a scheduled job, or a lazy check on the next dispatch. Track acceptance rate per agent for fairness and incentives.

F4Show the customer a live ETA and the agent on a map.

F5Add payments: when do you charge, and what happens on cancellation?

Answer

Authorise the payment when the order is placed, which holds the amount on the card. Capture it when the restaurant accepts, or on delivery. Cancellation then depends on the state:

  • A customer cancelling while PLACED: void the hold.
  • The restaurant rejecting or cancelling: void or refund in full.
  • After pick-up: no cancellation, only a support refund.

Put these side effects on the transitions: an onEnter hook per state, or subscribers to order.status_changed. The state table stays the single source of truth, and the payment calls go through an outbox so a crash doesn't lose them.

F6A restaurant gets 200 orders in the lunch rush. How do you stop it being overwhelmed?

Answer

Add capacity-based throttling. Each restaurant has a limit on orders in progress (ACCEPTED plus PREPARING). When it's full, it either disappears from search or shows a longer ETA and a "busy" badge. Placing an order checks the count (an index on restaurant + status) and returns 422 "restaurant busy". Better still, the restaurant controls the limit from its tablet. An auto-reject timer (if PLACED for more than 5 minutes, reject and refund) stops orders waiting forever.

  • Permission checks scattered through if/else in every endpoint. Put the actors into the transition table.
  • Checking state before identity. A stranger learns the order's status from a 409.
  • Assigning an agent in two steps with an await in between. One agent gets two orders.
  • A queue that stops at the first order it can't assign. One far-away restaurant blocks every order behind it.
  • Letting a busy agent go offline. The order is stranded.
  • Reading menu prices at delivery time. Copy them into the order when it's placed.

H5. High-level design

Two planes. The order plane (gateway → order service → Postgres → Kafka) is transactional. The location plane (realtime gateway → location service → Redis GEO → tracking fan-out) is high-volume and is allowed to lose a ping. Dispatch joins the two.

  • Cells by city. Each city (or a group of small ones) has its own order database shard, Redis GEO and dispatch workers. Orders and partners rarely cross cities, so one city's outage doesn't spread.
  • Order plane: every transition is UPDATE … WHERE id AND status = expected, plus an outbox row. Restaurants and partners get pushes. Notifications consume events.
  • Location plane: partners keep a persistent connection. Pings are validated (speed and jump filters), written to Redis GEO with a TTL (a stale partner simply disappears), and streamed to Kafka for history and ETA training.
  • Tracking: when an order has a partner, the tracking service subscribes to that partner's position channel and forwards updates to the customer's socket through the realtime gateway.

The dispatcher never writes order state directly. It asks the order service to assign, and the conditional update guarantees one partner per order.

H7. Detailed component design

1 · Location ingestion

  • Partners send batched pings over a persistent connection (MQTT or WebSocket). That's cheaper on battery and bandwidth than an HTTP request every 4 s.
  • The location service drops implausible points (a jump of 2 km in 4 s) and writes GEOADD geo:{city} lng lat partnerId and HSET partner:{id} lastSeen …. A sweeper runs ZREM on partners not seen for 30 s.
  • 75k writes a second across around 20 city shards is ~4k/s per Redis, which is easy. Pings also go to Kafka (partitioned by partner) for history.
  • The alternative is H3 or geohash cells (cell → set of partners), which let you query neighbouring cells at fixed resolutions and shard by cell. Redis GEO uses geohash internally anyway.

2 · Dispatch

  • Trigger: OrderAccepted, timed so the partner arrives as the food is ready: start searching at about prepTime − travelTime.
  • Candidates: GEOSEARCH within 3 km, filtered to status = FREE. Score each by travel ETA (from the ETA service), how well its arrival matches the ready time, and fairness (time since the partner's last order).
  • Batching: dispatch collects orders for 10–30 s and solves the assignment for the whole batch (minimum total cost, for example the Hungarian algorithm) instead of greedily one at a time. That's F2 in the LLD.
  • No double offers: SET partner:{id}:offer orderId NX PX 30000 before offering. Only one dispatcher can hold a partner, and the key expires on its own if the partner ignores the offer.
  • Accept: the order service runs UPDATE orders SET partner_id = $p, version = version + 1 WHERE id = $o AND partner_id IS NULL. If 0 rows change, someone else won, and the partner is released.

3 · Waiting queue and reassignment

An order with no candidates stays in a per-city queue (the orders_waiting_partner index), and dispatch retries it every 10 s with a wider radius and a bonus incentive. This is the LLD's dispatchWaiting, run on a schedule. A partner who goes offline mid-order triggers reassignment from the current position of the food (at the restaurant, or with the partner, which needs ops to step in).

4 · Live tracking fan-out

  • When an order has a partner, the tracking service subscribes to loc:{partnerId} (Redis pub/sub, published by the location service). Each update is forwarded to the order's channel at the realtime gateway, which pushes it to the customer's socket.
  • Throttle to one update every 5 s per order, and send the ETA only when it changes by more than a minute.
  • 350k sockets need ~10–20 gateway nodes with sticky routing. A node failure means clients reconnect and get a fresh snapshot.

H8. Interviewer questions and counters

Q1Why Redis GEO and not PostGIS?

Answer

75k position updates a second is a write rate that would fill a relational database with dead rows, and the data is only valuable for seconds. Redis keeps the latest position in memory, and radius queries take milliseconds. PostGIS is the right tool for the durable shapes: restaurant delivery zones and city polygons.

Push-back: "Redis dies, and you've lost every partner's location."

For about 4 seconds: the next round of pings rebuilds it. That's exactly why this data can live in a store that doesn't need to be durable. Run it with a replica for faster failover. Dispatch pauses briefly, and the order data is untouched.

Q2How do you stop one partner being assigned two orders at once?

Answer

Two guards. A short-lived offer lock per partner (SET NX PX) stops two dispatchers offering the same partner. A conditional update on the order (WHERE partner_id IS NULL) stops two partners taking the same order. Stacking orders (two orders from one restaurant on one trip) is a deliberate batching decision, not an accident.

Q3Nearest partner first is simple. Why do anything more complex?

Answer

Nearest-first per order is locally optimal and globally poor. It sends the only nearby partner to order A when order B, next door, had nobody else. Batching orders over a short window and minimising total pickup time does measurably better. Also, the "nearest" partner is useless if the food won't be ready for 20 minutes: what matters is arriving close to the ready time.

Push-back: "Batching adds 20 s of delay."

Food takes 15 minutes to prepare, so 20 seconds of dispatch delay is invisible. Start dispatch based on prep time, and batch when the window allows.

Q4When do you charge the customer?

Answer

Authorise (or take payment) before the order reaches the restaurant, so the kitchen never cooks an unpaid order. If the restaurant rejects or nobody can deliver, refund or void the authorisation automatically. Cash on delivery skips the step, and those orders need risk limits per customer. F5 in the LLD has the state details.

Q5WebSocket or polling for tracking?

Answer

WebSocket, or SSE: one connection per live order, pushed every 5 s. Polling every 5 s from 350k clients is 70k requests a second, with each one doing authentication and routing. Push costs memory per connection, but almost no CPU between messages. Keep polling as the fallback for networks that block WebSockets.

Q6The restaurant doesn't respond to a new order.

Answer

Escalate on timers: push again at 60 s, an automated phone call at 2 minutes, auto-cancel and refund at 5 minutes, and mark the restaurant "busy" so it stops getting orders. These timers are scheduled jobs keyed by order id (the job scheduler from Part 1), and each one runs only if the order is still PLACED. The conditional update guarantees that.

Q7Why partition by city? What about orders near city borders?

Answer

Almost every order, restaurant and partner belongs to one city, so a city is a natural failure and scaling boundary. Border areas get assigned to one city's cell. A partner who crosses over moves cell when their status is FREE. Global things (user accounts, payments, restaurant catalogue) live outside the cells.

Q8GPS is noisy: the partner jumps around the map, and ETA flips between 5 and 15 minutes.

Answer

Filter on ingest (drop impossible speeds, weight by reported accuracy), snap to the road network for display, and smooth ETA with hysteresis: only show a change above a threshold that persists for two updates. Positions shown to the customer are presentation, so smoothing them is fine. Dispatch uses the raw latest point.

Logging Framework

A logging library in the style of log4j or pino. Code asks for named loggers (app.orders.payment), and each logger inherits its level from its dotted parents, which you can change at runtime. Each record goes through a chain of processors (redaction, filtering) and then to every appender whose own threshold it passes. The appenders are console, an in-memory ring buffer, and a buffered decorator for slow sinks. Request context such as requestId rides along through every await via AsyncLocalStorage, so nobody has to pass it around. A small API exposes the logger levels, a log-writing endpoint and a log search.

7. Senior follow-ups

L1Logs from 200 pods: how do you collect and search them?

Answer

Don't ship logs from inside the app. Write JSON lines to stdout, which this framework's console appender already does. A node agent (Fluent Bit, Vector) tails the container output, adds pod, node and service labels, and ships to the store: Loki (cheap, label-indexed) or Elasticsearch (full-text). The app stays simple, and a slow log backend can never block requests. Correlate across services by passing requestId (or a W3C traceparent) in headers, and put it in each service's LogContext.

L2Writing to a file synchronously is slowing requests down.

Answer

That's exactly what BufferedAppender is for: requests only push onto an array, and a timer or the batch size triggers the write. For files, use a write stream (fs.createWriteStream, with flags: 'a') and respect backpressure: if write() returns false, stop flushing until the 'drain' event fires. For very high volume, move formatting and writing to a worker thread (pino's transport model), so even JSON.stringify leaves the main thread. Always flush on shutdown; the module does so in onApplicationShutdown.

L6The context leaks between requests sometimes. Why?

Answer

AsyncLocalStorage follows the async chain from the point where run() started. Context is lost or leaks in three situations:

  • Work scheduled outside run(). A shared connection pool or a cached promise created by another request carries that request's context.
  • Callback libraries that don't propagate async context. Old ones may need AsyncResource.bind.
  • LogContext.set() with no store. Calling it outside a request silently does nothing.

The interceptor here subscribes inside run() for exactly this reason: subscribing outside would start the handler without the store. For background jobs, call run({ jobId }) at the job boundary.

8. Pitfalls

  • Building the message before checking the level: log.debug(JSON.stringify(big)) does the work even when DEBUG is off.
  • String concatenation instead of fields. Logs become unsearchable. Use a message plus structured fields.
  • Logging secrets: tokens, passwords, card numbers, full request bodies. Redact centrally, before any appender sees them.
  • An appender error that bubbles up. A full disk becomes 500s on every request.
  • Unbounded in-memory buffers. A log storm becomes an out-of-memory crash. Bound them, drop low levels, count the drops.
  • Dropping ERRORs under load, or not flushing on shutdown. You lose exactly the lines you need.
  • A global static logger configured at import time. Untestable and impossible to reconfigure. Use one instance owned by the app.
  • Passing requestId through every function signature. Use AsyncLocalStorage.
  • Computing effective levels by walking the hierarchy on every call without a cache. Or caching without clearing the cache on setLevel.

H5. High-level design

Logs move through buffers at every hop: the library's ring buffer, the agent's disk buffer, Kafka. Each hop can absorb a slow next hop for a while without pushing back on the app.

  • Library (the LLD): writes structured JSON to stdout through a bounded asynchronous appender. It adds request id, trace id and service, and redacts known keys.
  • Agent per node: tails container output, adds Kubernetes labels (namespace, pod, service), batches, compresses, and buffers to local disk when ingest pushes back.
  • Ingest gateway: authenticates the tenant, enforces quotas, rejects malformed batches, and produces to Kafka with acks=all. It returns 200 only after Kafka has the data, so the agent can safely advance its checkpoint.
  • Kafka decouples ingest from storage and lets several consumers read the same stream: processors, the alert engine and live tail.
  • Processors parse, redact, sample (keep 100% of WARN and above, 10% of DEBUG) and write to the hot store in bulk. Old data rolls over to object storage, then to an archive tier.
  • Query service splits a query by time and shard, runs the pieces in parallel against hot and cold storage, merges by timestamp, and enforces limits.

The processor commits its Kafka offset only after the store has the data. A crash means replaying a batch (a duplicate), not losing it.

H7. Detailed component design

1 · Client library: never block the app

This is the LLD: check the level before doing anything (lazy messages), put the record in a bounded queue, and let a background flusher write it out. When the queue is full, drop DEBUG and INFO first and keep WARN and above (the BufferedAppender policy), and increment a logs_dropped_total{level} metric so the loss is visible. A synchronous write to a slow disk or the network on the request thread is the classic way logging causes an outage (L2).

2 · Agent and backpressure

  • The agent checkpoints its read position per file and advances it only after ingest returns 200. That gives at-least-once delivery across restarts.
  • If ingest returns 429 or 503, or is unreachable, the agent spills to a disk buffer (for example 5 GB per node, roughly an hour) and retries with jittered backoff. That way the agents don't all reconnect at the same moment when ingest recovers.
  • When the disk buffer is full, drop by priority and report the drops as metrics. Never fill the node's disk: that would kill the pods logging to it.

3 · Ingest, quotas and Kafka

  • Per-tenant token buckets in MB/s, with a burst allowance. A noisy team gets 429s, and its agents buffer, without affecting anyone else.
  • Kafka topics are partitioned by hash(tenant, service), so lines from one stream stay ordered, with enough partitions (say 512) to scale consumers. Ordering across streams is by timestamp, decided at query time.
  • Processors are a consumer group. Lag is the key health metric and drives autoscaling.

4 · Redaction

  • Layer 1, in the library: known keys (password, cardNumber, authorization) are masked before the line exists. This is redactKeys from the LLD.
  • Layer 2, in the pipeline: regex and pattern detectors for card numbers (with a Luhn check), Aadhaar or PAN formats, emails and tokens. Matches are masked, and the event is counted per service so the owning team gets a ticket to fix it at the source.
  • Raw data never reaches storage. If you need the unredacted line for debugging, the answer is to log better fields, not to keep secrets.

5 · Query execution

  • Parse the query. Use the label selector and time range to find chunk ids from the index, then drop chunks with the bloom filter if there's a trace id or request id.
  • Split the work by time into 15-minute pieces, run them in parallel across querier pods, stream results back merged by timestamp, and stop at the limit.
  • Guardrails: a maximum time span per query (24 h unless you go through an async export), a maximum bytes scanned per tenant per minute, and a cache for repeated dashboard queries.

Q1Why put Kafka between the agents and storage? Agents could write directly.

Answer

Three reasons. It absorbs bursts and outages in storage, which is the most fragile part (indexing, compaction), without pushing back on 20k agents. Several consumers can read the same stream: storage, the alert engine, live tail, a SIEM. And storage can be replayed after a bug. Without it, every storage hiccup becomes agent buffering on every node.

Push-back: "Kafka is another big system to run."

True. Below a few hundred MB/s, agents writing straight to the store with disk buffers is a reasonable start. Add Kafka when you need fan-out or the store can't absorb bursts.

Q2Elasticsearch or a Loki-style store?

Answer

It depends on how people query and on budget. Full-text indexing of everything costs about 20× more at this volume (H3), and most queries are "this service, this time window, this string", which label filtering plus a scan handles well. So I'd use the label-indexed store by default, plus a small full-text tier for recent errors.

Push-back: "Our engineers search across all services for a customer id."

Then that field needs an index. Use per-chunk bloom filters on it, or send a copy of the logs with that field to a columnar store keyed by it. Pay to index the one field you search on, not every word.

Q3Why not just use metrics and traces? Logs are expensive.

Answer

They answer different questions. Metrics tell you that something is wrong (cheap, aggregated). Traces tell you where (sampled request paths). Logs tell you why (detailed events). Reduce log volume by moving counts into metrics, sampling DEBUG, and raising levels at runtime only when needed (the LLD's PUT /loggers/{name}/level, L3). Putting trace ids in log lines connects all three.

Q4The whole logging pipeline is down. What happens to the apps?

Answer

Nothing visible. The library writes to stdout asynchronously, and the agent buffers to disk for about an hour. Beyond that the agent drops low-priority lines and counts them. No application thread ever waits for the pipeline. The cost is a gap or delay in logs, which is an observability incident, not a customer incident.

Push-back: "Audit logs must not be lost."

Audit events don't belong in the best-effort log pipeline. Write them to the database transactionally (an outbox) or to a durable topic with acknowledged writes. Different guarantee, different path.

Q5One team suddenly logs 10× more and slows everyone down.

Answer

Per-tenant quotas at ingest (429 for that tenant only), separate Kafka partitions so their lag doesn't block other teams' consumers, and per-tenant query limits. Alert the team on their own drop and throttle metrics. If they need more, it's a budget conversation, and you can show cost per team because volume is tracked per tenant.

Q6Are logs in order?

Answer

Within one stream (one pod's output), yes: one Kafka partition, one chunk sequence. Across pods, only roughly, by timestamp, and clocks drift by milliseconds. For causality across services, use the trace id and span parent links, not timestamps. The query merges by timestamp and breaks ties by stream and sequence, so results are at least deterministic.

Q7How do you make sure no card numbers end up in storage?

Answer

Defence in depth: typed log fields with masking in the library, pipeline detectors that mask and report, a periodic scan of samples from storage, and a code review rule against logging whole request bodies. Report each detection to the owning team, because masking in the pipeline hides the bug without fixing it.

Q8Alert when checkout logs more than 50 errors a minute. Run it as a query every minute?

Answer

No. Evaluate it on the stream: the alert engine consumes Kafka, keeps a sliding-window counter per rule and group key, and fires on the threshold with deduplication and a cool-down. Polling queries would scan storage every minute for every rule, and they'd be late by the ingest delay. For rate-style alerts, it's even better to emit a metric from the library and alert in the metrics system.
