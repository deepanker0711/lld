The three sentences to say

  1. Thin controllers, logic in services. Services import no HTTP code, so they are unit-testable and reusable from a queue consumer or cron job.
  2. Storage behind IRepository<T>. Moving to Postgres means one new class and one provider binding. Services don't change.
  3. Domain errors, not HTTP errors. Services throw ConflictError; one filter maps it to 409. The domain doesn't know it is behind HTTP.

G1How would you move this from memory to a database?

Answer

Services depend on IRepository<T>. I write a TypeORM implementation of the same interface and change one provider binding. The interface becomes async, because DB calls are.

Implementation change

  • Make every repository method return a Promise and add await in services. This is the one real ripple, so mention it.
  • Add a TypeORM entity with indexes for every findAll(pred) you rely on. A predicate scan in memory becomes a WHERE with an index.

G2What breaks if you run three instances behind a load balancer?

Answer

Everything held in process memory: data, counters, locks, timers. Each instance would have its own copy. State moves to a shared store, locks become distributed or DB-level, and timers become a shared queue.

Concurrency and correctness

G3Node is single-threaded. Why do you need a lock at all?

Answer

A synchronous block can't be interrupted, so check-then-act without an await in between is already safe. Once there is an await between the check and the write (payment call, DB call), another request runs in the gap and sees the same free slot. KeyedMutex queues callers per key.

G4The client retries a POST after a timeout. How do you avoid doing it twice?

Answer

Idempotency key. The client sends an Idempotency-Key header; the server stores key → response and returns the stored response on a repeat. Also store a hash of the body and return 422 if the same key comes with a different body.

LRU Cache

A fixed-capacity key-value store that evicts the least recently used key when full. Get and put in O(1). The repo version adds named caches, per-key TTL, stats, and a pluggable eviction policy.

Core structureHash map + doubly linked list
Complexityget / put / delete O(1)
PatternsStrategy, Factory, Observer
Demo filerequests/lru-cache.http

1. Problem and scope

Clarifying questions to ask

AskAssumption we build with
Capacity by number of keys or by bytes?Number of keys. Bytes is a follow-up (S4).
Does put on an existing key count as a use?Yes. It updates the value and moves the key to most recent.
Does reading the key list change recency?No. Only get and put do.
Do we need expiry?Optional per-key TTL plus a per-cache default.
One cache or many?Many named caches, each with its own capacity.
What's the value type?Any JSON value.
Concurrency, multiple servers?Single process for now; distributed is a follow-up (S6).

Requirements

  • Functional: create/list/delete caches; put, get, delete keys; list keys in recency order; stats (hits, misses, evictions, expirations, hit rate). Put reports which key it evicted.
  • Non-functional: O(1) get/put; eviction is deterministic; no background thread needed for correctness.

Why put checks liveEntry first

If the key exists but has expired, liveEntry removes it, so the slot is free and nothing gets evicted. Checking entries.has(key) instead would treat a dead key as live and overwrite it. That's subtle; mention it if you're asked about TTL.

7. Senior follow-ups

S1Why not just use a JavaScript Map? It keeps insertion order.

Answer

You can: on access, delete then set moves the key to the end, and map.keys().next() is the oldest. It's O(1) and much shorter. Say you know it, then explain why you built the list: it shows you understand the structure (most interviewers want that), it works in languages without ordered maps, and the explicit list is what you extend for LFU or segmented LRU.

Implementation change

map-only LRU
S2Add LFU eviction. Keep it O(1).

Answer

Track a frequency per key and a bucket per frequency, each bucket being an LRU list (ties break by recency). Keep minFreq. On access, move the key from bucket f to f+1 and bump minFreq if bucket f emptied. Evict the tail of the minFreq bucket. A new key always resets minFreq to 1.

Implementation change

  • New LfuEvictionPolicy implementing the same interface; add LFU to the enum and one case in the factory. Cache, service and controller don't change. This is the payoff of the Strategy split.
domain/lfu-eviction.policy.ts
S3Expired keys sit in memory until someone reads them. Fix that.

Answer

Lazy expiry keeps reads O(1) but leaks memory for keys nobody reads. Add active expiry: a periodic sweep. Redis does both: lazy on access plus a sampler that checks 20 random keys with a TTL ten times a second and repeats if more than 25% were expired. A full scan is O(n) per tick; a min-heap on expiresAt makes each sweep O(k log n) for k expired keys.

Implementation change

cache.ts + service lifecycle
S4Limit by memory (MB) instead of number of keys.

Answer

Estimate each entry's size on put and keep a running total. Evict in a loop until the new entry fits. One large put can evict many keys, so put becomes O(evicted). Reject a single value bigger than the whole budget.

Implementation change

cache.ts
S5A hot key expires and 1,000 requests hit the database at once. Prevent it.

Answer

That's a cache stampede. Use single-flight: the first miss starts the load and stores the in-flight promise; every other miss for the same key awaits that promise. Two extra options to mention: refresh slightly before expiry (early or probabilistic refresh), and add jitter to TTLs so many keys don't expire at the same moment.

Implementation change

cache-manager.service.ts
S6Make it distributed across several nodes.

Answer

Partition keys across nodes with consistent hashing (a hash ring with virtual nodes), so adding a node only moves about 1/N of the keys. Each node runs its own LRU. Add replicas for availability. In practice, use Redis Cluster (16,384 hash slots) with maxmemory-policy allkeys-lru. Redis's LRU is approximate: it samples a few keys and evicts the oldest of the sample, which avoids keeping a global list.

Implementation change

  • Keep CacheManagerService's public methods; put a CacheStore interface behind them with InMemoryCacheStore (today's code) and RedisCacheStore.
  • Redis mapping: SET key value PX ttl, GET, DEL; stats from INFO stats (keyspace_hits, keyspace_misses, evicted_keys).
  • Named caches become key prefixes (cache:users:a). Per-cache capacity isn't native in Redis; say so, and either use one Redis per cache class or count keys per prefix yourself.
consistent hashing sketch
S7The cache sits in front of a database. How do writes work?

Answer

StrategyHowTrade-off
Cache-asideApp reads cache, on miss reads DB and fills cache. On write: update DB, then delete the key.Most common. Brief staleness possible.
Write-throughWrite to cache and DB together.Consistent reads; slower writes.
Write-backWrite to cache; flush to DB later.Fast writes; data loss on crash.

Why delete instead of update on write: two concurrent writers can update the cache in the opposite order from the DB, leaving the cache wrong until expiry. Deleting means the next read loads the current value.

Implementation change

  • Cache-aside is getOrLoad from S5 plus cache.delete(key) after every DB write in the owning service. An onEvict hook is where write-back would flush dirty entries.
S8Is it safe if two requests hit the same cache at once?

Answer

Yes, in Node. Every Cache method is synchronous, so each call runs to completion before another starts and no interleaving is possible. In Java or Go you would need a lock around get/put (even get mutates the list), or striped locks per segment for throughput, which is what Caffeine and Guava do.

Implementation change

  • None today. If a method gains an await (for example a remote loader), only that path needs KeyedMutex or single-flight.
S9Scan resistance: one batch job reads a million keys once and wipes out the hot set.

Answer

Plain LRU is vulnerable to that. Segmented LRU (SLRU) has a probation segment and a protected segment: new keys enter probation, a second hit promotes them to protected, and eviction takes from probation first, so one-time keys never push out hot ones. W-TinyLFU (Caffeine) adds a frequency sketch to decide admission.

Implementation change

  • New SlruEvictionPolicy holding two DoublyLinkedLists and a Map<K, {node, segment}>. It reuses the list class unchanged, which is a good reason to have written it.

8. Pitfalls

  • Forgetting to update recency on put of an existing key.
  • Evicting when the key already exists (overwrite must never evict).
  • Removing from the Map but not the list, or the reverse. Every removal path (delete, expire, evict) must update both.
  • Letting GET /keys or stats change recency.
  • Capacity 0 or negative accepted. Validate in the DTO and in the domain constructor.
  • Using Date.now() directly, which makes TTL untestable without sleeps.
  • Counting expirations as evictions in stats. They are different events.

60-second summary to say

Say this

"Cache owns values, TTL and stats; eviction is a Strategy, so LRU is one class and LFU is another. LRU is a hash map to list nodes plus a doubly linked list with sentinels: get and put are O(1). Expiry is lazy on access, with an optional sweeper. Time comes from an injected Clock so tests don't sleep. Node runs each call to completion, so no locks are needed; to scale out I'd shard with consistent hashing or use Redis Cluster with allkeys-lru, and add single-flight in front of the database to prevent stampedes."

7. Senior follow-ups

U1The counter lives in one process. How do ten servers generate codes?

Answer

Three options. A DB sequence or Redis INCR is simple but makes every create a network call. Range allocation is the usual answer: each server claims a block of 1,000 ids from the DB in one atomic update and hands them out locally, so one DB write per 1,000 links; a crash wastes at most a block, which is fine. Snowflake-style ids (timestamp + machine id + sequence) need no DB but are ~11 base62 chars.

Implementation change

  • The CodeGenerator interface becomes next(): Promise<string>, and create becomes async. Nothing else in the service changes.
range-code.generator.ts
U2Sequential codes let anyone enumerate every link. Fix it.

Answer

Either switch to RandomCodeGenerator (the retry loop in generateFreeCode already handles collisions), or keep the counter and scramble it with a reversible permutation: multiply by a large number coprime with 62ⁿ, modulo 62ⁿ, then base62. Still collision-free, no longer sequential. Also rate-limit lookups that return 404, which is what scanning looks like.

Implementation change

  • One line in the module: { provide: CODE_GENERATOR, useClass: RandomCodeGenerator }. This is the Strategy split paying off.
U3Reads are 100× writes. How do you make redirects fast?

Answer

Cache-aside in front of the DB lookup: code → { longUrl, expiresAt }. Links almost never change, so the hit rate is very high. Also cache misses briefly (negative caching), so a bot hammering random codes doesn't hit the DB each time. Delete the cache entry when a link is deleted. At the edge, a CDN can serve the 302 itself, at the cost of click counts.

Implementation change

service, reusing the LRU Cache class
U4Writing clicks = clicks + 1 per redirect overloads the DB. Fix it.

Answer

Batch. Count in memory per code and flush every few seconds with one UPDATE … SET clicks = clicks + n per code. A crash loses a few seconds of counts, which is acceptable for analytics. For full analytics (referrer, country, device) publish a click event to Kafka and aggregate in a separate store; the redirect path never waits on it.

Implementation change

click-buffer.ts
U5Someone creates a million links with a script, or links to phishing pages.

Answer

Rate-limit creation per client (the rate limiter chapter, used as-is). Check URLs against a blocklist / Google Safe Browsing before saving, and re-check on redirect so links that turn bad later can be disabled. Require auth for custom aliases to stop squatting.

U7What happens to expired links?

Answer

They return 410 and keep their code forever, because reusing a code would send old links to a stranger's page. A daily job can move expired rows to cold storage in batches (WHERE expires_at < now() LIMIT 1000, using the partial index), but the code stays reserved, for example in a compact "retired codes" table or a Bloom filter checked during generation.

U8301 or 302?

Answer

301 is permanent and browsers cache it, so repeat clicks never reach the server: less load, but no click counts, and deleting or expiring a link has no effect for anyone who already clicked it. 302 (or 307) always comes back to us. We need analytics and expiry, so 302, plus Cache-Control: private, max-age=0 to stop intermediaries caching it.

  • Allowing an alias that equals a route name; it can never be reached.
  • Handing out someone's custom alias or temporary link through dedupe.
  • Not normalizing URLs, so https://A.com and https://a.com/ get two codes.
  • Reusing expired codes.
  • Accepting javascript: or ftp: URLs. Restrict to http(s).

7. Senior follow-ups

P1Four entry gates, each on its own server. Two cars arrive for the last slot.

Answer

The "it's one synchronous block" argument only holds inside one process. Across servers, the database must decide. Three options: claim with SKIP LOCKED (each gate locks a different free row, nobody waits); conditional update (UPDATE slots SET vehicle_number = $v WHERE id = $id AND vehicle_number IS NULL, 0 rows → pick again); or unique constraints (one_active_ticket_per_slot and one_active_ticket_per_vehicle) so the losing insert fails and you retry. Use the constraints regardless: they also stop the same car entering at two gates.

Implementation change

park in one statement
P2The lot has 20,000 slots. Allocation and availability are scans.

Answer

Keep a min-heap of free slots per (lot, type), ordered by (floor, number): park is a pop, unpark is a push, both O(log n), and "nearest" is the top. It's the same MinHeap as the job scheduler. Keep counters per (lot, floor, type) updated in the same code path as the slot change for O(1) availability. The strategy interface changes from "choose from a list" to "take from a pool", which is why a strategy that needs to see every slot (spread across floors) would keep its own structure.

P5Let users reserve a slot for 6 PM. Handle no-shows.

Answer

Reservations are time ranges, so a slot is no longer just free or occupied "now". A no-show is lazy: a reservation not used within a grace period (15 min) counts as expired when read, so the slot frees without a timer; optionally charge a no-show fee. 8. Pitfalls

  • Vehicle → slot fit as nested if/else: every new vehicle type edits the service. Use the lookup table.
  • An isFree flag next to vehicleNumber: two fields that can disagree. Derive free from the occupant.
  • Not normalising the vehicle number: KA01AB1234 and ka 01 ab 1234 both get tickets.
  • Checking "already parked" only in this lot: the same car is in two lots at once.
  • Fee with floats, or Math.round instead of Math.ceil: 61 minutes billed as 1 hour; 0 minutes billed as 0.
  • Freeing the slot before the payment succeeds: a declined card leaves a free slot with the car still in it.
  • Locking without re-reading inside the lock: the second request waits, then acts on the stale ACTIVE it read before waiting.
  • Adding a mutex to code with no await and calling it "concurrency handling": it does nothing in one process. Say why.
  • Availability as counters updated in several places: one missed decrement and the board lies forever.
  • Leaking another lot's ticket with 403: it confirms the ticket exists. 404.

8. Pitfalls

  • Checking the balance against allotted − used only. Several pending requests then overdraw it. Reserve the days at apply time.
  • Storing leave dates as Date or TIMESTAMPTZ. Midnight IST is the previous day in UTC, so dates shift by one. Use date-only strings or DATE.
  • Using new Date().toISOString().slice(0, 10) as "today". That's the UTC date. Between 00:00 and 05:30 IST it's yesterday.
  • Counting calendar days (to − from + 1) instead of working days, or forgetting holidays.
  • An exclusive overlap test (<). Leaves of Nov 3–5 and Nov 5–6 share the 5th and must clash.
  • Counting REJECTED or CANCELLED leaves as overlaps. The employee can then never re-apply for those dates.
  • Checking state before authorization. A peer learns "this leave is already approved" from a 409 instead of getting 403.
  • A PATCH { status } endpoint with if/else on the target status. Use a transition table and one action per move.
  • Refunding into pending when cancelling an approved leave, or into used when cancelling a pending one. Pick the move from the old status.
  • Recomputing days when approving. A holiday added in between changes the cost of a request the employee already saw.
  • Approver id taken from the request body in production. It must come from the token.
  • Calling the notifier directly from the service. Then every new consumer (payroll, calendar) edits LeavesService; publish an event instead.

"Employees have a manager, and a balance row per leave type per year with allotted, used and pending, created from the quota the first time it's needed. R1Three app servers behind a load balancer. Each has its own buckets, so a client gets 3× the limit.

Move per-client state to Redis. The read-refill-write must be atomic, otherwise two servers read 1 token at the same time and both allow. Boundary burst: with 100 per minute, a client sends 100 at 0:59 and 100 at 1:00, so 200 in two seconds. R6Where should rate limiting live: gateway or service?

Answer

In layers. At the edge or API gateway: coarse per-IP limits that stop floods before they cost anything (and DDoS protection, which is a different tool). R7Is there a race condition in your in-memory version?

Answer

No. tryConsume is synchronous from read to write, and Node runs one callback at a time, so two requests can't interleave inside it. The race appears the moment the state is remote: GET then SET from two servers can both see the last token. Hence the Lua script in R1 (or MULTI with WATCH, which retries on conflict).

R8Behind a load balancer, every request has the same IP.

Answer

req.ip is the proxy's address unless Express is told to trust it. Set app.set('trust proxy', 1) (the number of proxy hops you control) so req.ip comes from X-Forwarded-For. Never trust that header blindly: a client can send its own, so only the hops you control count. Prefer authenticated ids wherever possible.

8. Pitfalls

  • Refilling with setInterval per client. It doesn't scale; compute from elapsed time.
  • Logging blocked requests in the sliding log, which locks out a client that keeps retrying.
  • No cleanup, so memory grows with every client ever seen.
  • Not sending Retry-After; clients then retry in a tight loop.
  • Rate limiting in an interceptor or the handler, after validation already ran.
  • Floating-point drift: compute elapsed × limit / window, not elapsed × (limit / window).
  • Using Date.now() directly, which makes every test sleep.

N1The process crashes after saving the deliveries but before publishing. What happens?

The rows exist but no event does, so they stay PENDING forever. Saving to the DB and publishing to a broker are two systems, and no transaction covers both (the dual-write problem). Use the transactional outbox: write the delivery and an outbox row in the same DB transaction; a relay reads unpublished outbox rows, publishes them, and marks them sent. The relay can publish twice, which is fine because the consumer is idempotent. A cheaper safety net is a sweeper that re-publishes PENDING deliveries whose next_attempt_at has passed; that also recovers retries lost in a restart.

N2Run five dispatcher instances. How do you stop two of them sending the same delivery?

The in-memory status !== PENDING check is the same idea, but it's only safe in a single process. With SQS the visibility timeout hides a message from other consumers while one works on it, but duplicates still happen, so keep the DB claim. A worker that dies mid-send leaves the row in SENDING; give the claim a lease and let a reaper put expired ones back to PENDING (same as the job scheduler's J2).

N8The provider was down for 10 minutes. 50,000 deliveries all retry at the same second.

8. Pitfalls

  • Sending inside the request: one slow provider makes every POST slow, and a provider outage becomes your outage.
  • Thinking EventEmitter.emit() is async. It calls listeners synchronously; defer with setImmediate or use a real queue.
  • Validating after storing: a 400 leaves half-created notifications behind. Check everything first.
  • Rendering at send time from the live template: retries can send different text, and "what did we send?" has no answer.
  • !data[name] as the missing-variable check: rejects 0, false and ''.
  • Re-expanding rendered output: user data containing {{secret}} pulls in other variables.
  • Retrying permanent errors: a hard-bounced address gets three more emails and your sender reputation drops.
  • One delivery row for all channels: one failing channel blocks or re-sends the others.
  • A consumer that doesn't check status: a duplicate event sends the email twice.
  • Handling success inside the send's try: a bookkeeping bug becomes a retry, which re-sends the message.
  • Booleans with enableImplicitConversion: "no" becomes true. Use @RawValue().
  • Spreading a partial DTO over preferences: undefined values overwrite true. Filter them out.

Run jobs once, after a delay, or every N ms. Due jobs come off a min-heap ordered by (runAt, priority, seq), a tick loop starts them on a bounded worker pool without awaiting, failures retry with exponential backoff, recurring jobs follow a fixed grid, and cancel is lazy.

7. Senior follow-ups

J1Run three scheduler instances. How do you stop two of them running the same job?

Answer

The in-memory heap can't be shared, so the queue moves to the database and each worker claims rows atomically. FOR UPDATE SKIP LOCKED lets each worker lock different due rows without waiting on the others; the claim and the status change happen in one statement. Alternatives: leader election (one instance schedules, others idle) or BullMQ/Redis (delayed jobs in a sorted set scored by runAt, moved atomically to a ready list by a Lua script).

Implementation change

  • Replace MinHeap + tick()'s peek/pop with a claimDue(limit) query; enqueue becomes a no-op (the row is the queue). Completion code is unchanged apart from writing to the DB.
claim query
J2A worker crashes halfway through a job. What happens?

Answer

In memory: the job is lost. With a DB, the row is stuck in RUNNING. Give every claim a lease (locked_until); long jobs extend it with a heartbeat. A reaper puts expired leases back to SCHEDULED. That makes delivery at-least-once: the job may run twice (it crashed after sending the email but before marking it done), so handlers must be idempotent, e.g. pass jobId as the provider's idempotency key. Exactly-once is not achievable across a network; at-least-once + idempotency is the standard answer.

J8Lazy cancel: what if 90% of the heap is cancelled jobs?

Answer

Memory grows and each tick pops more garbage. Count stale entries; when they pass half the heap, rebuild from the live jobs. Building a heap from n items with bottom-up heapify is O(n), not O(n log n). 8. Pitfalls

  • await-ing the handler inside the tick loop: the "pool" silently becomes one job at a time.
  • A fire-and-forget Promise without .catch: one bookkeeping bug becomes an unhandled rejection and kills the process.
  • Changing runAt/priority of a job while it sits in the heap: the invariant breaks with no error. Pop, change, push.
  • Swapping with the wrong child in sift-down (must be the smaller one).
  • items.shift() in pop: O(n) and it breaks the parent/child indexes.
  • Recurring next run = finishedAt + interval: drifts later every cycle; firing every missed slot after downtime: bursts.
  • Handling success inside the same try as the handler: a bug in bookkeeping retries a job that already succeeded.
  • Counting "queued" with heap.size under lazy cancel: overcounts.
  • Retrying with no backoff: a failing dependency gets hammered by every job at once (add jitter in production).
  • setInterval(this.tick, …): loses this. Use an arrow function.

"A job is data: a type that names a handler, plus a payload. Handlers are strategies collected in a registry, so a new job type is one class.
